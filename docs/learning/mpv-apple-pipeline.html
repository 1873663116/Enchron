01心智模型：拉式（pull-based）五层管线

在动手看任何代码之前，先建立一张正确的地图。mpv 是一个拉式播放器：渲染时钟在最末端拉动整条流水线——需要下一帧时，才回溯去解码、去解复用、去读字节。一帧视频要穿过五个职责清晰的分层。

LAYER 1
Stream 流抽象

把「字节从哪来」抹平：文件 / HTTP / SMB / WebDAV 都变成统一可读字节流。stream/

LAYER 2
Demux 解复用

拆容器，分出视频/音频/字幕轨，切成带时间戳的 packet。demux/

LAYER 3
Decode 解码

压缩 packet → 原始像素 frame。委托 FFmpeg。video/decode/vd_lavc.c

LAYER 4
Filter 滤镜

对 raw 帧做去隔行 / 格式转换 / 裁剪。filters/ · video/filter/

LAYER 5
VO + 渲染

色彩管理、YUV→RGB、HDR、缩放、抖动、上屏。video/out/

核心概念

packet 与 frame 的分界，就是「解码」这个动作本身。Demux 产出的是 packet（仍是 H.264/HEVC 压缩比特），Decode 产出的是 frame（可直接显示的原始像素，通常是 YUV）。记住这条分界线，后面所有「在哪里发生零拷贝」「硬解输出什么」的问题都能定位。

mpv 的 player/ 核心（如 player/video.c）不亲自解码，它是调度者：负责把这五层串起来、做音视频同步（A/V sync）、管理时间戳、决定何时该拉下一帧。真正的「重活」——解复用和解码——都委托给 FFmpeg。

03输入侧：Stream 与 Demuxer

视频文件不是「一种东西」，而是两层正交的概念叠在一起：容器装着轨道，轨道用某种编码压缩。理解这一层，才能理解为什么 XrPlayer 能同时支持本地、SMB、WebDAV。

定义

Stream（流抽象，stream/）：mpv 把「数据来源」统一成一个可 seek、可读的字节流接口。每种协议是一个 stream 实现——本地文件 stream_file.c、网络协议大多直接走 FFmpeg 的 stream_lavf.c（覆盖 http/https/rtmp/rtsp/hls）。

为什么这对 XrPlayer 重要上层 demuxer 根本不关心字节是从 SSD 还是从 SMB / WebDAV 来的。只要能提供字节流，mpv 就能播。这正好对应 FileBrowsing 模块「本地 / SMB / WebDAV」多数据源设计——数据源差异在 stream 层就被吸收，不会污染解码与渲染。

定义

Demuxer（解复用器，demux/）：读取 stream，识别容器格式，把交织在一起的多条 elementary stream（视频轨、音频轨、字幕轨）分离出来，并切成带时间戳（PTS 显示时间戳 / DTS 解码时间戳）的 packet。mpv 绝大多数容器委托 FFmpeg 的 demux_lavf.c，少量内建（mkv 的 demux_mkv.c 等）。

关键区分

容器格式 ≠ 编码格式（二者正交）

维度容器 / Container编码 / Codec
例子.mp4 .mkv .mov .ts .webmH.264 HEVC AV1 VP9 / AAC FLAC
规定什么如何把多条轨道、时间戳、元数据、字幕打包进一个文件单条轨道的数据如何被压缩
谁处理DemuxerDecoder

同一个 .mkv 里可以装 HEVC 视频 + FLAC 音频；同一段 H.264 流既能放进 MP4 也能放进 TS。先解容器拿到 packet，再按 codec 解码成 frame。

04解码侧：FFmpeg、VideoToolbox 与零拷贝

这是整条管线里 Apple 平台特性最浓的一段。核心问题只有一个：解码出来的像素，落在哪块内存？答案决定了后面能不能做到零拷贝。

4.1 FFmpeg / libavcodec 的角色

事实

mpv 本身不写视频解码器。它的解码层 video/decode/vd_lavc.c（"lavc" = libavcodec）是对 FFmpeg libavcodec 的封装。FFmpeg 是 mpv 解码与解复用的事实引擎；mpv 提供调度、硬解选择（hwdec）、滤镜接入、输出与渲染。

4.2 软件解码 vs 硬件解码

软件解码（CPU）

用 CPU 跑 libavcodec，输出 raw frame 落在系统内存（RAM），典型格式 yuv420p / p010。通用、不挑硬件，但 4K/8K/HEVC/AV1 时 CPU 与功耗代价大。

硬件解码（GPU / ASIC）

把熵解码、反量化、运动补偿交给专用解码块。输出帧留在 GPU 可访问内存，CPU 几乎不碰像素。省 CPU、省电，能扛 4K/8K HDR——这是 Vision Pro 长时间观看的刚需。

4.3 Apple 平台的硬件解码：VideoToolbox

定义

VideoToolbox（VideoToolbox.framework）是 Apple 的底层硬件编解码框架，直接访问硬件解码器。FFmpeg 内建 VideoToolbox 后端，mpv 通过它使用。

  • hwdec=videotoolbox —— 启用硬件解码，解码后的帧保留在 GPU 内存（CVPixelBuffer 形式），用于零拷贝渲染。官方要求搭配 --vo=gpu/gpu-next（macOS）或 --vo=libmpv（iOS 9+）。
  • hwdec=videotoolbox-copy —— 硬件解码后把帧拷回系统 RAM。多一次 GPU→CPU 拷贝，换来与任意 VO / 软件滤镜的兼容性。这会破坏零拷贝。
命名澄清AVHWDeviceType（如 AV_HWDEVICE_TYPE_VIDEOTOOLBOX）是 FFmpeg 的概念，不是 Apple API——它表示「用哪类硬件设备上下文做加速」。别把它和 AVFoundation 混淆。

4.4 CVPixelBuffer、IOSurface 与零拷贝

原理

CVPixelBuffer（Core Video 的像素缓冲对象）是 VideoToolbox 解码输出的每一帧的载体。在 Apple 平台上它通常由一个 IOSurface 背书——IOSurface 是内核级、可跨进程 / 跨框架共享的 GPU 内存缓冲。正因为帧落在 IOSurface 上，Metal 才能直接把它当纹理用，无需复制。

零拷贝（zero-copy）：指像素数据从解码到渲染不发生 CPU 内存拷贝。解码器写进 IOSurface，渲染器（Metal）直接引用同一块 IOSurface 生成纹理。videotoolbox 是零拷贝路径；videotoolbox-copy 多一次回拷，破坏零拷贝。

4.5 解码输出的像素格式

视频几乎都以 YUV（亮度 Y + 色度 U/V）存储，且色度常被下采样为 4:2:0 以省码率；而屏幕需要 RGB，所以渲染阶段必须做 YUV→RGB 转换。常见格式：

格式布局位深典型场景 / CVPixelBuffer 类型
yuv420p平面 planar 4:2:08-bit软件解码，住在 RAM
NV12半平面 semi-planar（Y 一面，UV 交错一面）8-bitApple 硬解 SDR · 420YpCbCr8BiPlanar
p010半平面 4:2:010-bitHDR10 / HLG · 420YpCbCr10BiPlanar

硬解时 FFmpeg/VideoToolbox 把帧封进 CVPixelBuffer，其内部布局就是 NV12（8-bit）或 p010（10-bit）；mpv 拿到的是封装在 FFmpeg AVFrame 里、pixel format = AV_PIX_FMT_VIDEOTOOLBOX 的这个 CVPixelBuffer。

05渲染侧：VO、libplacebo，以及「mpv 与 Metal」的真相

这一节是全文的认知关键点。很多人以为 mpv 在 Apple 上「用 Metal 渲染」——这个说法不准确。理解真相，才能理解 XrPlayer 为什么配置成 gpu-api=vulkan。

5.1 VO 抽象与两个 GPU 渲染器

定义

VO（Video Output，video/out/）是输出驱动抽象，每个 VO 实现一个 vo_driver。两个 GPU 渲染器：

  • vo_gpu —— 旧的、mpv 自带的 GPU 渲染器，自写 shader 链，抽象在多种图形 API 之上。
  • vo_gpu_next —— 新一代渲染器，基于 libplacebo（libplacebo 最初就是从 mpv 渲染管线剥离出来的独立库）。上游推荐的高质量路径，HDR / tone mapping / 色彩处理更好。XrPlayer 原生路径用的正是它。

5.2 mpv 渲染到底做了什么（「自渲染」的价值）

这正是「播放器自己渲染、而不直接交给系统 AVPlayer」的理由。mpv（尤其 gpu-next/libplacebo）的 shader 链做：

处理原理
色彩空间转换YUV→RGB（按 BT.601/709/2020 矩阵），处理 primaries、transfer function、range（limited/full）。libplacebo 内部统一升采样到 4:4:4 再处理。
HDR tone mapping把 HDR（PQ/HLG，BT.2020）映射到目标显示能力，多种曲线可选。
缩放 scaling高质量重采样核（ewa_lanczos、spline 等），远胜系统默认双线性。
debanding去除低码率/平滑渐变区的色带（banding）。
dithering 抖动量化到目标位深前做 gamma 正确的抖动，避免引入新 banding。
沉浸场景为何必须自渲染系统视频层（AVPlayer）只能放矩形画面。要把视频贴到 180/360 球面、曲面巨幕等任意几何上，必须拿到 GPU 纹理自己摆放——这是 SpatialScene 存在的根本前提。

5.3 libmpv 的 render API

当你把 mpv 嵌入自己的 app（正是 XrPlayer 的场景），不用 mpv 自带窗口，而用 libmpv render API：mpv_render_context_create() 把渲染交还给你的 GPU 上下文。官方 header（include/mpv/render.h）里只定义了两种 API type：

// include/mpv/render.h —— 官方仅有的两种渲染后端
#define MPV_RENDER_API_TYPE_OPENGL  "opengl"   // OpenGL
#define MPV_RENDER_API_TYPE_SW      "sw"       // software，输出到一块内存 buffer

// 注意：不存在 MPV_RENDER_API_TYPE_METAL

5.4 真相：上游 mpv 没有原生 Metal 后端

已查证
  • --gpu-api 的合法取值只有 opengl / vulkan / d3d11（加 auto），没有 metal。
  • 源码 video/out/ 下只有 opengl/ vulkan/ d3d11/ 三个后端，没有任何 metal 目录。
  • libmpv render API 没有 Metal type（见上）。

那 mpv 在 Apple 上怎么用到 GPU？答案是 MoltenVK：一个把 Vulkan 调用翻译成 Metal 的库。设 gpu-api=vulkan + gpu-context=moltenvk，mpv 以为自己在跑 Vulkan，实际命令被 MoltenVK 转译给 Metal 执行。

重要边界macOS/iOS 上的 MoltenVK 不含视频解码扩展。所以即便渲染走 Vulkan→Metal，解码仍然必须用 VideoToolbox。解码与渲染是两条独立的硬件路径：VideoToolbox 解码 → IOSurface → MoltenVK/Metal 渲染。
visionOS 的现实约束另两条路也走不通：OPENGL 依赖 OpenGL ES，而 visionOS 不支持 GLES；纯 SW 软渲有 CPU 拷贝与性能代价。因此 visionOS 上的现实路径就是 VideoToolbox 解码 + gpu-next 经 MoltenVK 渲染进 CAMetalLayer——这正是 XrPlayer 的选择。

06Apple 框架：从 CVPixelBuffer 到 MTLTexture 的零拷贝桥

解码侧产出 CVPixelBuffer，渲染侧需要 MTLTexture。这两者之间不需要复制——靠的是它们共享同一块 IOSurface。这是整个 Apple 视频栈零拷贝的物理基础。

框架关系
框架提供什么
VideoToolbox硬件编解码，产出 CVPixelBuffer
Core VideoCVPixelBuffer（像素缓冲，IOSurface 背书）、CVMetalTextureCache（CVPixelBuffer↔MTLTexture 零拷贝缓存）
IOSurface底层共享内存缓冲，让 VideoToolbox / Core Video / Metal 共享同一块像素内存而不复制
MetalMTLTexture GPU 纹理；CAMetalLayer 把 Metal 渲染结果上屏
原理

CVMetalTextureCache 如何零拷贝转 MTLTexture

  1. 解码得到 CVPixelBuffer（内部 NV12/p010，由 IOSurface 背书）。
  2. 调 CVMetalTextureCacheCreateTextureFromImage()，传入 CVPixelBuffer + plane 索引 + Metal 像素格式。
  3. Core Video 不复制像素，而是基于底层 IOSurface 创建 CVMetalTexture，从中取出 MTLTexture——和原 CVPixelBuffer 指向同一块内存。
  4. NV12 取两个 plane：plane 0（Y，r8）、plane 1（CbCr，rg8）；p010 用 r16/rg16。然后在 Metal shader 里做 YUV→RGB。
本质零拷贝靠的是 IOSurface 这块共享内存被多方「引用」而非「拷贝」。这是理解整条 Apple 视频管线效率的那把钥匙。

07visionOS 输出侧：把帧变成空间表面上的像素

最终一步：一块 MTLTexture 如何成为 Vision Pro 眼前的画面。visionOS 提供了三条出口，对应窗口、空间材质、沉浸式三种场景。

出口是什么适用场景
CAMetalLayer把 Metal drawable 直接上屏的 layerWindow 窗口里的平面画面
TextureResource.DrawableQueue给 RealityKit 材质创建可动态更新的 drawable 队列；取出 Drawable（内含 MTLTexture），写入帧后 present 刷新材质视频贴到 entity 材质
LowLevelTexturevisionOS 2.0+ 的自管理纹理容器，可直接用 Metal 写入其底层 MTLTexture 再绑材质，比 DrawableQueue 更底层灵活需要 compute shader 处理帧（XrPlayer 采用）
Compositor Services LayerRenderer在 ImmersiveSpace 里直接驱动 Metal，拿到逐眼 drawable 自己绘制并 present完全自定义的沉浸式几何 / 立体渲染
典型流程

hwdec=videotoolbox 出 CVPixelBuffer → CVMetalTextureCache 取 Y/CbCr 纹理 → Metal compute/blit 做 YUV→RGB（或叠字幕/OSD）写入 LowLevelTexture / DrawableQueue 的 MTLTexture → 贴到空间表面材质 → RealityKit 合成到空间。

输出侧的最终答案无论哪条路，最终产物都是一块 GPU 纹理（MTLTexture）或一个 drawable：窗口 → CAMetalLayer drawable；空间材质 → DrawableQueue/LowLevelTexture；沉浸式 → Compositor 的逐眼 drawable。

08本仓库的实际形态：XrPlayer 如何落地这条管线

前面是通用原理，这一节是 XrPlayer 仓库里的真实代码。它做了一个聪明的选择：让 mpv 用完整的 gpu-next 管线渲染（含全部色彩/HDR 处理），再把渲染好的 drawable 纹理捕获下来喂给 RealityKit——而不是让 mpv 只解码、自己重写一套渲染。

8.1 mpv 初始化与关键配置

PlaybackCore/Adapters/MPV/MPVPlayerAdapter.swift · MPVConfiguration.swift

// MPVConfiguration —— 原生 GPU 输出路径的关键选项
("vo",          "gpu-next")          // libplacebo 渲染器
("hwdec",       "videotoolbox")      // 零拷贝硬解（回退路径用 videotoolbox-copy）
("hwdec-codecs","all")               // H.264 / HEVC / VP9 / AV1...
("vd-lavc-dr",  "yes")               // direct rendering，零拷贝输出
("gpu-api",     "vulkan")            // ← 不是 metal！
("gpu-context", "moltenvk")          // Vulkan 经 MoltenVK 翻译成 Metal
("fbo-format",  "rgba16f")           // HDR 半精度浮点输出
("target-colorspace-hint", "auto")  // HDR 色彩空间直通
("tone-mapping", "auto")

初始化时（ensureMPVReady()）通过 mpv_set_option(handle, "wid", …) 把一个 CAMetalLayer 指针交给 mpv，让 gpu-next 直接渲染进这个 layer。

8.2 原生路径 vs 软件回退（两条腿）

路径 A · 原生 GPU（gpu-next）

Shared/MPVNativeMetalLayerView.swift

mpv (gpu-next) → MoltenVK/Vulkan → MPVNativeMetalLayer(CAMetalLayer)。该 layer 重写 nextDrawable() 记录 lastVendedDrawable，供空间桥读取。配置：pixelFormat=.rgba16Float、framebufferOnly=false（允许读回）、wantsExtendedDynamicRangeContent=true（HDR）。

路径 B · 软件回退（libmpv）

Shared/MetalVideoRenderer.swift

mpv 软渲出 CVPixelBuffer，经 FrameOutput.didOutputFrame() 送达 MetalVideoRenderer（MTKView delegate），用 CVMetalTextureCache 取纹理、Metal shader 做 NV12→RGB / 直渲 BGRA。

8.3 空间桥：从 drawable 到 RealityKit 材质

SpatialScene/Renderers/PanoramaLayerBridge.swift

这是 XrPlayer 把「窗口画面」升级为「空间画面」的关键。一个 CADisplayLink 每帧：

// 每个显示刷新

8.4 运行时元数据决策

立体布局、球面投影、HDR 类型不是写死的，而是运行时从 mpv 属性探测（docs/reference/2026-04-06-mpv-metadata-investigation.md）：

  • 立体布局：video-params/stereo-in → sbs2l/sbs2r/ab2l/ab2r
  • 球面投影：metadata/by-key/GSpherical:* + 宽高比启发式
  • HDR 类型：gamma（pq/hlg）+ primaries（BT.2020）+ scene-max-* 动态元数据

09可信度标注与仍需在设备上验证的点

学习材料要分清「已查证的事实」与「工程推断 / 选型」。下面诚实标注边界。

已确证 verified

  • mpv 五层分层与目录（stream/ demux/ vd_lavc.c filters/ video/out/）。
  • 视频解码委托 FFmpeg libavcodec；demux 委托 libavformat。
  • hwdec=videotoolbox 保留 GPU 帧、-copy 回拷 RAM（官方 options.rst）。
  • libmpv render API 只有 OPENGL 与 SW，无 Metal type。
  • 上游 mpv 无原生 Metal 后端；--gpu-api 只有 opengl/vulkan/d3d11；macOS Metal 只能经 MoltenVK，且 MoltenVK 无解码扩展。
  • vo_gpu_next 基于 libplacebo；其 YUV→RGB / tone mapping / debanding / dithering / scaling 能力。
  • CVMetalTextureCache 经 IOSurface 零拷贝转 MTLTexture。
  • RealityKit DrawableQueue 与 LowLevelTexture 存在且用于动态纹理。
  • XrPlayer 仓库配置：vo=gpu-next, gpu-api=vulkan, gpu-context=moltenvk, hwdec=videotoolbox，及 PanoramaLayerBridge 捕获 drawable → LowLevelTexture 的实现。

待验证 / 工程选型 verify on-device

  • 你实际使用的 MPVKit-GPL 构建是否打了自定义 patch（上游主线无 Metal，但分支可能有胶水层）——以仓库 docs/reference/mpv-build-guide.md 为准。
  • visionOS 上 mpv 帧 → RealityKit/Compositor 的最佳路径选型（DrawableQueue vs LowLevelTexture vs Compositor Services）官方无 mpv 专门指引，需以零拷贝/掉帧/HDR 实测裁决。
  • AVHWDeviceType 命名按 FFmpeg 文档复核（AV_HWDEVICE_TYPE_VIDEOTOOLBOX）。
  • HDR 端到端正确性（PQ/HLG 标签直通、EDR 元数据、UnlitMaterial 不二次 tone map）需在真机以 HDR 片源验证——build pass / Simulator 正确都不是 HDR 正确性证据。

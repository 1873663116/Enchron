# Enchron Product Atlas

Enchron Product Atlas 是面向人类理解与记忆的只读交互式产品图谱。它从 Enchron 一手文档派生，不产生、修改或覆盖产品事实。

## 信息层级

Atlas 以用户体验与产品状态为主视图。状态变化、不变量、领域所有权、编译边界和验证依据从可见产品行为逐层展开；普通 API、类型和文件不属于默认视觉内容，除非它们本身构成产品或架构合同。

完整覆盖指每项正式产品语义都能找到对应的状态、关系、所有者与依据，不指复制全部文档文字或展示全部代码元素。

Atlas 的产品世界由大致对应真实 Enchron 界面的解释性界面组成。它保留 Media Library、Window Playback、Docked、Panorama、Environment Card 与 Settings 等产品表面的空间关系和正式操作，但不追求像素还原，也不执行真实产品行为。

第一层空间布局按实际 visionOS Scene 容器组织：Main Window 承载 Media Library、Settings 与 Window Playback；Environment Card 使用独立 Volume；Enchron Immersive Space 承载 Enchron Environment、Docked Video Surface 与 Panorama；Player Controls Window 承载空间播放控制。Home View、System Surroundings 与 Apple System Environment 位于 Enchron 容器之外，作为 visionOS 管理的外部世界。

每个解释性操作都映射到 `Product Action Registry` 中的稳定动作身份。Registry 记录动作所在界面、可用条件、触发结果、失败结果、所有者、文档来源和 Atlas 呈现位置；同一正式动作可以在多个解释性界面中出现。机械验证检查每个动作具有有效 placement、placement 指向已登记的 surface/region，并检查来源与状态引用；浏览器验收负责确认这些 placement 是否真的形成清晰、完整的解释性投影。机械验证不声称证明运行时页面已经展示了每个动作。

`Product State Registry` 与 `Product Action Registry` 是 Atlas 的唯一语义模型。解释性界面只投影选定的产品状态和可用动作，不分别复制状态说明；动作演示只改变 Atlas 的讲解状态，不执行真实 App 行为。模型必须排除互相矛盾的状态组合。

点击解释性操作后，Atlas 先识别该行为真正改变或保持的逻辑主语，再选择能够直接解释它的图形。操作前、过渡、操作后与异常分支仍需完整覆盖，但不得被强制塞进一套统一卡片或面板；发生变化的关系本身应成为主要视觉内容，文字只承担名称、必要条件、原因、所有者、验证与来源。

正常路径默认展开。失败、系统中断和其他边界条件以始终可见的分支入口折叠展示，并由 `Product Action Registry` 登记和验证；视觉折叠不得成为语义遗漏或隐藏入口。

每段行为讲解都以稳定的责任层表达用户、Enchron 与 visionOS 的因果关系。继续深入时，Enchron 展开为 Media Library、Playback、Presentation 与 Environment 等领域所有者，再展开为 Target、Module、平台 API 与验证入口；不得在产品层直接堆叠代码名称，也不得只用颜色代替责任关系。

## 视觉语言

Atlas 使用 visionOS 风格的空间产品蓝图：通过克制的玻璃感、层次和稳定空间关系帮助记忆，但不复刻真实 App，不退化为传统工程流程图或卡片仪表盘。中文承担解释，正式英文术语保留为稳定名称；视觉美感服务于产品关系和状态变化，不用装饰掩盖信息。

Atlas 依据所解释信息的逻辑性质自动路由到三种视觉语言，不提供把同一内容换皮的全局主题选择：

- **A · 空间旅程**用于产品行为与用户路径。产品世界和动作讲解先回答用户从哪里出发、触发了什么、产品经过什么过渡、最后到达哪里；保持不变的身份沿路径连续显示，失败或系统接管从路径本身分叉。
- **B · 系统蓝图**用于静态结构、visionOS Scene 容器、责任边界和所有权。它回答行为发生在哪个容器、Enchron 与 visionOS 分别负责什么、哪个领域与编译边界拥有相关合同；连接线只表达真实依赖或承载关系。
- **C · 状态机器**用于状态、约束、生命周期、异常和恢复。它回答当前状态是什么、哪些转换合法、转换事务如何提交或回滚，以及系统中断后哪些资源延续或消失。

同一功能可以从 A 的产品过程继续下钻到 B 的结构依据，再下钻到 C 的状态合同，但三个层级不能同时堆在同一画布中。下钻只改变当前解释层，不改变产品语义，也不把 A、B、C 作为用户自行挑选的视觉主题。D 式产品分镜不属于 Atlas 的视觉语言。

每项动作必须在唯一语义模型中用 `visualLayers` 登记实际成立的解释层和依据。A 是动作的产品入口；B 只有在人工判断结构关系有解释价值，且动作具有真实 UI Surface、Scene Container 或 System Context placement 及所有者时成立，登记在 `behavior` 或 `semantic-rule` 的位置不能伪装成空间承载；C 只有在动作具有非空状态变化，并且 guard、生命周期、恢复或转换事务值得作为状态合同解释时成立。具备 placement 或 patch 只是允许登记相应层的必要依据，不会机械地产生 B 或 C；页面不得为缺少声明的动作生成这些层。

C 必须覆盖动作登记的全部 demonstrations 和 branches。每个 branch 在模型中显式登记 `visualSemantic`，区分替代结果、条件分支、可恢复失败、回滚、系统中断和未决问题；页面不能把所有失败统一画成回滚。稳定节点可以只显示少量关键状态，但每个阶段和分支的完整变化必须能够按需查看，并明确显示变化数量。

Atlas 不把同一种排版当作所有事实的默认答案。Window 与 Docked 之间的转换以同一 Media Session 和 renderer consumer binding 的空间迁移表达；Panorama 以 Projection 与 Stereo Layout 的正交坐标和显示几何展开表达；Home View 恢复以 App Process、Immersive Space 与仅内存恢复意图的不同生命周期表达。其他内容依据其因果结构选择轴、序列、关系图、生命周期线、状态差分或分支；只有缺少更具解释力的结构时才使用普通列表。

Atlas 默认使用适合长期阅读的白天外观：温和空间白和中性浅灰构成层次，黑灰文字承担信息，克制的玻璃只用于区分承载面，少量颜色只编码路径、状态和异常。暗夜外观遵循相同信息层级，使用中性炭灰而非蓝黑霓虹；初次打开遵循系统外观，用户可以在白天、暗夜与跟随系统之间切换。两套外观都不得依赖反色滤镜，也不得使用发光、终端化网格或装饰性的高科技视觉。

正式实现可以复用连续身份路径、转换路径、生命周期线、状态轴、空间表面、分支与来源标记等视觉原语，但不得为了复用组件而把不同逻辑压成同一种页面模板。不看说明文字时，读者至少应该能够指出什么保持不变、什么发生变化、谁造成变化，以及失败或系统中断通向哪里。

## 事实与交付状态

Atlas 默认展示已经确认的目标产品模型，并分别表达：

- 产品事实是否已经确认；
- 产品事实是否已经实现；
- 已实现行为是否已经验证。

设计、实现和验证不得合并为一个完成状态。尚未决策的内容必须显式呈现为缺口，不得由现有代码反向推定为产品事实。

产品知识不存在一个覆盖所有声明的单一依赖方向。已确认的产品决策与规范文档定义产品应当怎样工作，并约束代码实现；代码表达当前实现，测试表达可机械检查的合同与检查意图；只有在当前产品树上实际执行并满足验收规则的结果才能形成验证证据；Atlas 负责把这些已经校准的信息投影为人类可以理解的关系。

规范领先代码是合法状态，此时产品事实可以为已确认，而实现为部分实现、未发现或尚未评估，验证为尚无证据。已经确认的动作只通过 `delivery.implementation` 表达实现落差，不为尚未实现伪造产品异常分支。

代码中出现规范没有确认的产品行为时，不得直接创建 Atlas 正式动作。分歧先进入当前任务的交付报告；需要跨任务保留时，先写入拥有该产品事实的权威文档之显式未决部分，随后 Atlas 才能将它投影为未决缺口。代码与规范冲突也使用同一落点，直到实现被修正或产品决策得到确认。

`delivery.implementation` 的最小判定标准如下。它是有范围的人工代码审阅结论，Atlas V1 的机械验证不能证明该判断：

- `observed`：已经检查负责该行为的生产入口与实现路径，在检查范围内找到完整目标行为，且没有发现与规范冲突的缺口；
- `partial`：已经找到生产实现，但明确缺少规范要求的一部分行为或分支；
- `notFound`：已经检查命名的领域所有者、预期生产入口和相关搜索范围，没有找到生产实现；
- `notAssessed`：没有进行足以选择前三项的有范围代码审阅，或现有信息不足。

每次改变 implementation assessment，都必须在任务交付报告中列出实际检查的生产代码与测试路径、已知缺口和未检查范围。`observed` 只表示在该范围内看到了实现，不证明运行时行为正确；`notFound` 也不声称完成了全仓不存在性证明。

`delivery.verification` 的最小判定标准如下：

- `verifiedCurrent`：登记的证据明确绑定当前产品树身份，实际执行了该行为所需的验证层与通过条件，并直接覆盖当前动作；
- `historicalEvidence`：登记的证据直接覆盖该动作，但绑定的是历史、reference 或已经 stale 的产品树；
- `blocked`：登记的当前验证记录明确记载未能完成的验证范围、阻塞原因和对应 artifact，且没有形成通过结论；
- `notEvidenced`：不存在满足前三项条件的已登记证据；测试源码、规范、验证规则、构建成功或日志无错误均不足以提升该状态。

任何非 `notEvidenced` 状态都必须具有 `evidenceRefs`。每项引用严格只包含 `sourceId`、`heading` 与 `scope`；`scope` 必须说明证据实际覆盖的行为与验证层。证据文件必须先登记为 Atlas source，并完成独立来源审阅和 `accept`。规范文档、架构文档与验证规则可以定义通过条件，但不能充当运行证据。

## 权威与维护

Atlas 手工维护，不自动解析 Markdown，也不作为产品决策编辑入口。每个重要节点和关系必须引用对应的一手文档。已确认的产品事实发生变化时，先使拥有该事实的规范文档准确，再更新 Atlas；实现进展、当前验证结果和代码与规范的分歧则分别校准到对应状态，不能通过改写目标规范来消除差异。

Git 历史保存每个仓库版本对应的 Atlas。Atlas 的已审阅来源清单记录相关一手文件的 Git blob hash；维护工具比较该基线与当前内容，提示发生变化的来源、diff 和可能受影响的节点，但不自动修改 Atlas 语义。

机械脚本负责取得登记来源的 Git 状态、blob hash 与 diff，验证 Registry 的 placement、状态、`evidenceRefs` 和来源结构，并确定性生成网页；它不为代码库建立第二套内容基线，不判断文档或代码谁应当改变，也不证明 implementation assessment。仓库专属 Skill 负责在任务涉及的规范文档、代码、测试、验证证据与 Atlas 之间判断声明性质和语义影响，必要时更新各自拥有的内容，并通过浏览器检查实际解释性投影。

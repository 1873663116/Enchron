# 远程读取管线：完整流程

这份文档按数据流动的顺序说明 Enchron 远程播放的每一个环节：每一段的输入、输出、中间做了什么，以及它向远程服务端提出了什么要求、用什么方式提出。表格形式的模型定义与参数推导在 `docs/READ_PIPELINE_PLAN.md`，本文只讲那里无法用表格表达的因果关系。

## 全图

```
用户选一个远程文件
      │  源类型（WebDAV / SMB / Emby）+ 路径
      ▼
[文件浏览器]
      │  输出：内容长度 + 身份（ETag、字节数、修改时间）
      │  向服务端：PROPFIND Depth=1（WebDAV）或 Emby 的条目查询
      ▼
[源适配器]
      │  输出：同一个「按范围读」接口（stat / read(range)）
      │  向服务端：GET + Range 头；SMB 则是 SMB2 READ
      ▼
[字节流服务]
      │  输出：本机回环 URL + 一个读取管线实例
      │  注册期：读 4 KiB 量一次往返延迟
      ▼
[回环 HTTP  127.0.0.1]
      │  libbluray 在这里发 HTTP Range 请求
      │  输出：206 + Content-Range + 字节（不可寻址时 200 + chunked）
      ▼
[读取管线]
      │  输入：一个字节范围
      │  处理：探测、块对齐、缓存、并发、预取、超时、重试、对冲、熔断
      │  输出：按请求切好的字节
      ▼
[源适配器]  →  GET Range: bytes=a-b  →
      ▼
[远程服务端]（WebDAV / SMB 共享 / Emby）
      │  输出：206 + Content-Range + 字节，或 200 + 整文件
      ▼
[libbluray]  解析 UDF、读 playlist、解复用
      ▼
[播放引擎]  解码与呈现
```

管线只服务 libbluray 的随机读。libbluray 解出的视频与音频不再经过管线，所以管线里的块、并发、预取都是「文件读」的概念，不是「码流缓冲」的概念。

## 第一段：文件浏览器

输入是源与路径，输出是内容长度与身份。身份由 ETag、字节数、修改时间组成，之后所有缓存都以它作键。

对 WebDAV，这一段发一次 `PROPFIND`，`Depth: 1`，请求体是属性查询，认证放在 `Authorization` 头里。服务端返回 `207 Multi-Status`，Enchron 从中取每个条目的 `getcontentlength`、`getetag`、`getlastmodified`，并用 `resourcetype` 判断是目录还是文件。目录列举的上界取「三十秒」与「六倍延迟」中的较小者，超时即报错而不是无限等待。

对 Emby 类服务，这一段是条目查询，播放前还要拿到实际码流地址；码流地址上携带 `api_key` 查询参数，请求头再带 `X-Emby-Token`，Jellyfin 用 `MediaBrowser Token="…"`，Plex 用 `X-Plex-Token`。

对 SMB，这一段是连接建立与 `contentLength` 查询，走 SMB2/3 协议，没有 HTTP。

## 第二段：源适配器

输入是路径，输出是同一个「按范围读」接口。三种源各自实现，形状相同：给我一段字节范围，我给你这段字节，并告诉你内容长度。

这条接口是整个系统唯一知道具体协议的地方。管线只知道「读某段范围要多久、回来多少字节」。

## 第三段：字节流服务与回环

输入是适配器与身份，输出是一个本机回环地址与一个管线实例。

回环存在的原因是 libbluray：它要一个能随机读的文件，而 HTTP Range 正好是这个形状。回环把「文件随机读」翻译成「管线的一次读」，也把管线的错误翻译成 HTTP 状态码。

注册期这里做一次四 KiB 的读，量一个往返需要多久。这是唯一一次主动探测，代价是一次往返。

## 第四段：读取管线

管线的输入是一个字节范围，输出是这段字节。中间有六件事，它们共同决定「向服务端要什么」。

探测。延迟来自那次四 KiB 小读，之后随每次真实读更新。带宽来自真实读的统计：每次读完记录字节数与耗时，规划取最近三十秒采样率的低分位。同一链路实测在一分钟内从一点八摆动到十四 MB/s。

块对齐。管线不以请求为单位读，而以块为单位读。块大小是吞吐乘以延迟，下限六十四 KiB，上限为缓冲上限的八分之一。一个 2 KiB 的请求也会触发一整块的传输，因此「向服务端要多少」由块大小决定，不由请求大小决定。这是对服务端最直接的负载特征。

缓存。取回的块留在内存，总量不超过六十四 MiB，超了淘汰最久未用。命中不发请求。目录阶段的块在播放时仍然有用。

并发与预取。并发度是一个往返之内能塞下几个块，加一；实测在二到三之间。预取在播放位置之前多取几块，深度不小于并发度，实现上表现为「同时有若干个 GET 在飞」。

让位。需求读耗时中位数超过延迟四倍时，预取暂停；回落后恢复。这条规则来自一个实测缺陷：限速两 MB/s 时预取抢走百分之七十八的带宽，需求读只剩零点四五 MB/s。

鲁棒性。静默超过「三十秒」或「三倍延迟」中的较大者算超时，重试一次；同一块在超过两倍延迟仍未返回就并行再发一份，先回者生效；连续三次失败打开熔断，冷却取十倍延迟；内容身份变化时整份缓存作废。

## 第五段：Enchron 向服务端要什么

这一段回答「要什么数据、要多少、发几次」。所有数量都以块为单位。

列举阶段只要目录元数据，不要文件内容。WebDAV 是一次 `PROPFIND`，Emby 是若干条目查询，SMB 是一次目录枚举。

打开阶段要三类数据。第一是那次四 KiB 的延迟样本。第二是首块预取，实测二点六到四点四 MB，随吞吐变化。第三是 libbluray 解析 UDF 与 playlist 产生的随机读，它们被对齐成整块，实测目录段取回约十到二十 MB，耗时随吞吐在一秒半到五秒多之间。

播放阶段的读是顺序的，每次一块。吞吐十 MB/s、块五点七 MB 时，大约每秒一到两次请求，同时有三块在飞。

跳转阶段从目标位置重新对齐，实测取回八到二十六 MB，其中一部分是跳转之后继续播放的读取。

重试与对冲会让同一个范围被请求两次。这是设计上的代价：宁可多发一次，也不让首帧或跳转变慢。

这些请求都以 HTTP GET 发出，头里带 `Range: bytes=a-b` 与 `Accept-Encoding: identity`。`identity` 是必须的：任何压缩都会让字节偏移与文件偏移不再一一对应，随机读会被破坏。

服务端的回答必须是 `206 Partial Content`，并且 `Content-Range` 的起点与请求一致。Enchron 校验这两项，不一致就判失败，不把错位的字节往上送。内容长度从 `Content-Range` 的总长里读出。

若服务端忽略了 Range 而返回 `200`，Enchron 把这次读当作整文件返回，并把「可寻址」标记为假；上层因此不走随机读，而是顺序消费。这个分支是给不支持 Range 的服务器准备的，不是正常路径。

连接由 URLSession 复用，同一主机上同时只有二到三条连接，与并发度一致。SMB 走同一条 AMSMB2 连接上的偏移读，不经过 HTTP；Emby 的读同样是一次带 Range 的 GET，只是认证放在专有请求头里。

## 第六段：libbluray 与播放

回环把字节交给 libbluray。libbluray 解析 UDF、读 playlist、解复用出视频与音频；这些流不再经过管线。播放引擎负责解码与呈现。

因此管线的每一次读都对应「文件里的一段字节」，而不是「一帧画面」。理解这一点才能理解为什么参数是块、并发、预取。

## 本地源为什么不同

本地文件不走这条路。`file://` 直接交给 libbluray，用 POSIX 读，没有回环、没有探测、没有缓存层。

本地没有值得探测的东西：随机四 KiB 读零点一五毫秒，一 MiB 读零点五九毫秒，libbluray 打开期间全部读加起来不到两毫秒。在这条路径上加管线只增加开销。

## 时间花在哪里

打开由三段组成：解析（遍历索引的 CPU 时间）、预取（首块传输）、目录（UDF 与 playlist 的字节除以带宽）。吞吐高时目录段一点五到二秒，吞吐一点八 MB/s 时五秒以上。

起播是「从用户应答到首帧」：一个往返加首帧字节除以吞吐，再加解码器起播。实测一点零五秒。

跳转是一个往返加目标字节除以吞吐，再加解码器重建。解码时间用同位置重复跳转分离出来，三百一十二毫秒。

稳态看累积：内容需求减带宽供给，差值超过缓冲上限就开始停顿。带宽够时不停，不够时按带宽与码率的比值推进。

## 判定不成立的方向

打开前用布局探测定位元数据范围，经实测不成立：目录阶段的读本身就是 UDF 遍历，预先读更大范围只增加字节。

目录阶段开启预取也不成立：深度一的预取让目录从一点五五秒变成一点七九秒，还多读一点八 MB。

打开时缩小块大小不成立：块索引与块大小绑定，边播边改会让缓存与新块对不上，实测目录加载二十秒未完成。

## 尚未完成

带宽估计的稳定性是核心开放问题，所有由带宽推导的参数都受它影响，而源端在分钟级波动五倍。

验收矩阵有四行缺素材：MKV 与 MP4 没有文件，SMB 没有可用服务器，Emby 只有服务器身份摘要而没有保存的源与库条目。另有两行只是没有测：本地大量小文件、远程大目录首屏。

错误率与延迟抖动有采样但没有独立判据。

## 已知风险

预取让位的四倍延迟阈值是经验值，只有端到端证据。

限速器修复同样只有端到端证据；单元测试尝试失败后已删除。

跳转与起播的字节量都是上界口径。

## 复现方式

构建用 `xcodebuild build -project Enchron.xcodeproj -scheme Enchron -configuration Debug -destination id=<模拟器 UDID> -derivedDataPath .scratch/build`，安装必须走 `Scripts/build/install_to_simulator.sh`。

测试只跑相关场景：`-only-testing:EnchronDomainTests/<套件>`，覆盖容量探测、参数网格、吞吐模型、鲁棒性、静默策略与块大小稳定性，共二十四项。

运行期数据来自应用内计时日志与测试通道。计时日志包括 `disc.open.start`、`disc.open.resolved`、`disc.open.prewarm`、`disc.catalog.loaded`、`disc.open.ready`、`playback.command`、`playback.firstFrame`、`playback.seek.start`、`playback.seek.ready`。管线快照由 `pipelineStats` 读取，含需求与预取字节、块大小、并发度与规划吞吐。限速器只在 DEBUG 构建里存在，由 `throttle` 动词设置速率。

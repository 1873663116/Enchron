# Architecture Review: Known Issues Fix (P0-P2 UI Alignment)

## Review Summary

Plan is structurally sound. 9 units, 4 phases, dependencies correctly mapped. The geometric-not-hierarchical model for playback mode constraint is the right call. 7 P1 issues found, mostly gaps between what the plan says and what the code and HTML design actually need. No architectural rewrites required, just precision corrections.

## Technical Issues

### ISSUE-1 [P1]: Info bar removed with no destination

**Where:** ExecPlan Unit 1, "Remove info bar from controls ornament"

The HTML `player.html` has the info bar (back button + title + format metadata) as a **separate fixed header at screen top** (lines 421-448), NOT part of the bottom footer. Unit 1 correctly removes it from the bottom ornament but creates no replacement. Without the back button, users can't navigate back from playback without a gesture.

**Blast radius:** Navigation dead-end during playback. User must use system gesture to exit.

**Fix direction:** Add `PlayerInfoBarView()` as an overlay in the video ZStack area (MainView.swift, inside the `ZStack(alignment: .topTrailing)` block), gated on `appModel.showControls`, fading with `.transition(.opacity)` matching controls animation. Change alignment to `.top` with a leading-aligned HStack for back+title, trailing for close button.

### ISSUE-2 [P1]: Unit 4 file list misses 6 of 10 files

**Where:** ExecPlan Unit 4, "Files" section

Global search finds `.hoverEffect(.highlight)` in **10 Swift source files**, but Unit 4 lists only 4. Missing:

| File | Lines |
|------|-------|
| `PlayerInfoBarView.swift` | :20 |
| `BreadcrumbView.swift` | :35 |
| `FilterPillsView.swift` | :31 |
| `ScreenPositionControlView.swift` | :28 |
| `PlaylistView.swift` | :28, :80 |
| `NavigationOrnament.swift` | :33, :57 |

The plan's approach text says "Global search" which is correct, but the explicit file list misleads the implementing agent about scope.

**Fix direction:** Expand the Modify list to include all 10 files, 15 total occurrences.

### ISSUE-3 [P1]: Close button transition violates "pure opacity" goal

**Where:** MainView.swift:95-98

```swift
.transition(.asymmetric(
    insertion: .opacity.combined(with: .scale(scale: 0.8)).combined(with: .offset(y: -10)),
    removal: .opacity.combined(with: .scale(scale: 0.8))
))
```

This close/stop button is gated on `showControls`, same as the controls ornament. It uses scale + offset transitions, directly contradicting R8 ("no position shift"). Users will see the close button snap/slide while the ornament fades.

**Fix direction:** Change to `.transition(.opacity)` consistent with R8/R9.

### ISSUE-4 [P1]: All `withAnimation` sites need explicit curve, not just line 223

**Where:** ExecPlan Unit 5, MainView.swift

Unit 5 identifies only line 223 as missing `withAnimation`. But all 6 existing `withAnimation` calls (lines 154, 157, 172, 206, 211, 290-291) use bare `withAnimation {}` which applies SwiftUI's default spring animation. The ornament's `.animation(.easeInOut(duration: 0.4))` modifier handles the ornament content, but the close button overlay (ISSUE-3) and any future controls-gated elements need explicit `.easeInOut(duration: 0.4)` at the mutation site.

**Fix direction:** Update all 7 sites to `withAnimation(.easeInOut(duration: 0.4))`. This also resolves ISSUE-3's animation curve.

### ISSUE-5 [P1]: Right menu restructuring drops existing functionality

**Where:** ExecPlan Unit 2

The plan says Settings menu should contain only "Playback Mode" + "Environment" per HTML. But the current right menu (`rightMenu`, PlayerControlsView.swift:266-401) also contains:

- Projection override (Auto / manual projection types)
- Playlist navigation
- Screen Position control
- Settings window link
- Debug link (#if DEBUG)

These items serve real functions. Removing them breaks existing workflows. The HTML is a design reference for visual layout, not a feature kill list.

**Fix direction:** Keep all existing items in the right menu. Restructure the visual grouping (Playback Mode + Projection together, Environment section, then Playlist, then utilities). HTML popup styling applies to the container, not to content reduction.

### ISSUE-6 [P1]: NLE toggle removed from pill with unclear destination

**Where:** ExecPlan Unit 1 ("Remove NLE toggle from main bar"), Unit 2 (R3)

Unit 1 removes `NLETimelineToggleButton` from the pill. Unit 2's R3 says Settings popup has "Playback Mode, Environment." NLE toggle falls through the cracks.

**Fix direction:** Since the right menu retains all existing items (ISSUE-5), the NLE toggle can stay as a right-menu item with a "Timeline" label in a separate section. Or, given that NLE is a power-user feature accessed frequently during editing, keep it in the pill as the 6th button and accept a minor deviation from the 5-button HTML spec.

Auto-decision: Keep NLE toggle in the pill. The HTML shows 5 buttons for a design mockup, but NLE is a core differentiator and should be one tap away. Document the deviation.

### ISSUE-7 [P1]: Missing test for profile-pending mode state

**Where:** TestPlan SC-3 and ExecPlan Unit 6 boundary cases

Unit 6 mentions "MediaProfile not yet detected" as a boundary case but doesn't specify behavior. TestPlan has no test for it. This is a real user scenario: file opens, profile detection takes ~1s, user opens mode menu during that window.

**Fix direction:** Define behavior: when `projectionType` is unknown/default, show `[.window, .immersive]` (safe default, same as flat content). Add to TestPlan SC-3.

## Architecture Suggestions

### Controls animation data flow

```
showControls mutation
    ↓
withAnimation(.easeInOut(duration: 0.4)) {
    appModel.showControls = true/false     ← 7 sites in MainView
}
    ↓                          ↓
[Bottom ornament]         [Video overlay]
.animation(easeInOut 0.4)  .transition(.opacity)
    ↓                          ↓
PlayerControlsView        PlayerInfoBarView (ISSUE-1)
.transition(.opacity)     Close button (ISSUE-3)
```

All elements gated on `showControls` must use consistent `.transition(.opacity)`. The ornament has its own `.animation()` modifier, but overlay elements in the ZStack need explicit transitions.

### Mode constraint data flow

```
ProjectionType (from PlaybackCore)
    ↓
PlaybackMode.allowedModes(for:)     ← new static method (Unit 6)
    ↓                    ↓
rightMenu filter    DecidePlaybackModeUseCase.decideMode()
(UI filtering)      (validation on manual override)
    ↓
Only allowed modes shown / invalid override clamped to .window
```

This is clean. Constraint logic stays in PlayerUI per Architecture Invariant.

## Implementation Amendments

Based on the issues above, the following changes to ExecPlan are required:

### Unit 1 Amendment: Keep info bar, keep NLE toggle

- Do NOT remove `PlayerInfoBarView()` from `PlayerControlsView`. Instead, move it to a separate overlay in the video area (MainView.swift) with top-leading alignment, matching the HTML top header design.
- Keep `NLETimelineToggleButton` in the pill as the 6th button. Document deviation from HTML 5-button spec.
- Revised button order: Menu, Rewind 10s, Play/Pause, Forward 10s, NLE Toggle, Settings (6 buttons)

### Unit 2 Amendment: Keep all menu items

- Do NOT strip Projection, Playlist, Screen Position, Settings from the right menu.
- Apply HTML popup visual styling to the existing menu container.
- Add geometric constraint filtering to Mode section (per original Unit 6 plan).

### Unit 4 Amendment: Expand file list

Add these files to the modification list:
- `XrPlayer/PlayerUI/Views/PlayerInfoBarView.swift`
- `XrPlayer/FileBrowsing/Views/BreadcrumbView.swift`

- `XrPlayer/App/Navigation/NavigationOrnament.swift`

Total: 10 files, 15 occurrences.

### Unit 5 Amendment: Fix all 7 withAnimation sites + close button

- Update all 7 `showControls` mutation sites to `withAnimation(.easeInOut(duration: 0.4))`, not just line 223.
- Change close button (MainView:95-98) transition to `.transition(.opacity)`.
- Move `PlayerInfoBarView` overlay to video area with `.transition(.opacity)`.

### Unit 6 Amendment: Define profile-pending behavior

- When `projectionType` is not yet detected (default/nil), `allowedModes` returns `[.window, .immersive]` (safe default).
- Add TestPlan entry for this case.

### Unit 7 Amendment: Verify before adding GeometryReader

- WindowVideoView already calls `setNeedsLayout()` in `updateUIView` (line 56, added in commit f234be8).
- **First step:** Build and test in simulator to check if resize already works.
- GeometryReader only if `setNeedsLayout()` proves insufficient.
- If GeometryReader is needed, use `onChange(of: geometry.size)` with a size-delta threshold to prevent excessive relayout.

## NOT in scope

- **NLE pinch-to-zoom** (R20 drag refinement): Complex gesture, deferred per ExecPlan scope boundaries.
- **Custom popover for directional menus**: visionOS `Menu {}` doesn't support directional control. Popup direction follows system behavior. HTML's left/right expansion is aspirational; the system menu's default behavior is acceptable.
- **Right menu visual redesign**: Keep system `Menu {}` styling. HTML popup styling (glass background, border-radius, item padding) would require a full custom popover component, which is overengineering for bug fixes.
- **Seek bar custom track**: HTML shows a custom track (4pt height, 6pt on hover). SwiftUI `Slider` provides native behavior. Custom track deferred unless native Slider is visually unacceptable.
- **L1/L2 scope assessment**: Unit 9 correctly defers assessment to implementation time. If >10 files, separate PR.

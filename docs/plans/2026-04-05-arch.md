# 架构评审：文档清理与路径规范化

## 评审摘要

计划架构健康。4 个实施单元的依赖 DAG 正确，操作范围限定在文档/路径/git 索引。无 P0 阻塞。主要风险集中在数据精度（文件计数偏差）和两个边界情况（README 目录树条目、DESIGN-TO-SWIFTUI 引用验证缺失）。

## 技术问题

### P1-1: README.md/README.en.md 目录树条目需特殊处理

**文件:** README.md:106, README.en.md:106

```
  workspace-agents/     # 产品、架构、质量门禁与技能文档
```

这不是简单的路径替换。workspace-agents/ 被 git rm 后目录不再存在，此行是项目结构树的一部分。需要：
- 删除此行，或
- 替换为 `docs/` 条目（如果树中还没有 docs/ 行）

**爆炸半径:** 仅影响 README 的视觉结构，不影响 Agent 工作流。

**建议:** 检查 README 中是否已有 `docs/` 目录行。如有则删除 workspace-agents 行；如没有则替换为 `docs/` 行。Unit 2 实施时根据实际 README 结构判断。

### P1-2: TestPlan 缺少 R16 (DESIGN-TO-SWIFTUI) 引用验证

**文件:** docs/plans/active/TestPlan.md

AC5 只检查文件命名规范，不验证 DESIGN-TO-SWIFTUI 旧引用是否全部更新。需新增验收条件：

```bash
grep -rn "DESIGN-TO-SWIFTUI" .overnight/supervisor-prompt.md docs/solutions/ | wc -l
```

期望：0

**建议:** 更新计划中的计数。子项合计与总数的算术错误（94≠84）应修正。

### P2-2: 引用计数偏差

**文件:** docs/plans/active/ExecPlan.md

- 概述说"~45 处断裂引用"，实际按文件统计为 39 处
- CLAUDE.md 描述说"10 处 → docs/"，实际 9 处 → docs/（第 10 处是 known_issues 行删除）

**爆炸半径:** 无。每处引用在 Unit 2 中逐行处理，不依赖总数。

### P2-3: supervisor-prompt.md 更新时机

**文件:** .overnight/supervisor-prompt.md

此文件在 overnight 运行中被每轮 session 读取。更新路径引用不影响当前运行的 session（已加载到内存），下轮 session 会读到更新后的版本。安全执行。

## 架构建议

### 文档依赖图（确认正确）

```
Unit 1 (恢复 7 文件)
  ├──→ Unit 2 (修复 39 处引用)
  │       └──→ Unit 4 (重命名 + 更新 7 处 DESIGN-TO-SWIFTUI 引用)
  └──→ Unit 3 (目录重组 + git rm 98 文件)
```

Unit 2 和 Unit 3 互不依赖，理论上可并行。但文档操作成本低，顺序执行更安全、更易调试。

## Worktree 并行化策略

顺序实现，无并行化机会。所有 4 个 Unit 有严格依赖链，且均操作同一组文件的引用关系。文档操作成本极低（每 Unit 预计 < 5 分钟 CC 时间），并行化节省可忽略不计。

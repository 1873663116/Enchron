# 播放呈现层的平台约束

本文记录 `Modules/Playback` 里**无法从代码本身读出**的事实：RealityKit 与 SwiftUI 在 visionOS 上的实际行为、由缺陷换来的次序约束、以及若干领域模型为何要这样切分。能由代码或断言表达的部分不写在这里。引擎侧（解码、渲染器、时间线）的约束在 `docs/PLAYBACK_ENGINE_CONSTRAINTS.md`。

## RealityKit 的实测行为

- **Entity 进入场景后是异步激活的**。先建立所有权，再插入 entity，**只有在 entity 拿到最终拓扑之后**才安装渲染器组件。次序颠倒时 RealityKit 偶尔会接受一个尚未进入场景的 `VideoPlayerComponent` 而不提交它的渲染目标。
- **这条次序由一个有界轮询兜底**。`PlaybackSurfaceActivation` 订阅 `SceneEvents.DidActivateEntity`，但订阅建立前 entity 可能已经激活，事件便不会再来；`observe` 因此在每次换 entity 或新建订阅时都另起一个轮询任务，每 `retryIntervalForView`（25 ms）重跑一次就绪检查（`videoEntity.isActive` 等条件都成立才装组件），最多 `maximumRetryCountForView`（120 次，约 3 秒）后放弃。
- **共享的播放 Entity 只能从一条非活动链移入正在执行更新的那个 RealityView**。`Entity.isActive` 覆盖它的整条祖先链，因此这个判断不需要任何生命周期回调。
- **跨 RealityView 根的交接必须换新 Entity**。RealityKit 在 Window 与 Immersive 根之间移动之后，不能可靠地重新激活同一个 Entity 与 renderer graph。同一 ownership class 内部的转移则保持身份。
- **visionOS 27**：在 RealityView 场景之间移动 entity，可能留下旧的 current mode 而 requested mode 不变。激活后要在一个有界区间内重发请求，RealityKit 才会在新场景里开始转换。
- **`ContentTypeDidChange` 不标识它的来源 Entity**，RealityKit 也不承诺重新订阅后重放它。因此整个会话只保留一份订阅，用捕获的 media scope 充当 Apple 没有提供的实体身份。
- **组件写入只证明 RealityKit 接受了组件值**。给目标一个有界的提交区间，但**不要**对后续的 `VideoPlayerComponent` 变化去抖：Panorama 的模式协商会在同一个渲染目标仍在使用时持续改动组件。
- **重挂稳定播放 entity 不增删它的 `VideoPlayerComponent`**，所以不保证会有组件事件；attach 处的 active-entity 守卫仍然拦住"非活动目标场景被报告为就绪"。
- **刚安装的组件在分类期间合法地报告没有 current mode**，而重写同样的 desired 值会重启这次分类。所以先等是对的，但只能等到分类合理完成为止：设备实测一个正在落定的表面约一秒内报出模式，而在转换中途被交给替换技术会话的表面可能**永远**报 nil，没有上界就再也没有东西去重试它。
- **`realityScripting` 自带一个 targeted `SpatialTapGesture`** 用来给脚本喂 `TapGestureEvent`，它就在这个视图内部。普通的 `.gesture` 会把每一次捏合都输给它，必须同时识别（simultaneously）才能让脚本系统与播放都看到这次点击。
- **RealityKitScripting 的默认输入提供者在进程的第一个 RealityKit 场景创建时就请求 ARKit 授权**，也就是主窗口出现之时，与沉浸空间是否打开无关。Info.plist 里没有对应的 usage description 时，ARKitCore 在授权回调里抛 `NSInternalInconsistencyException`，app 启动两秒内以 SIGABRT 退出（2026-09-11 真机，崩溃栈 `__ar_session_request_authorization_block_invoke`）。产品不使用手部或世界感知，所以 `RKS.initialize(inputOptions: .all.subtracting(.ar))` 关掉它的 AR 输入提供者，而不是把已删除的 usage description 加回去；tap 与 drag 输入不受影响。
- **RealityKit 不激活留在编译后环境资源里的空 transform marker**。保留它的稳定身份与 authored 世界变换，但让它成为一个活的 RealityView 根，它的播放子节点才能激活。
- **给 entity 的 opacity 组件发同一个目标值，不能让正在播放的缓动重新起跑**。`setOpacity` 原先把新请求与组件的当前值比较，而当前值正被动画逐帧改写，于是 `RealityView` 每跑一遍 `update:` 都像收到一个新目标：一次淡入 panorama 的观测记录了十五到二十六次透明度写入，曲线反复经过 0.005、0.017、0.048、0.138、0.402、0.889、0.984、0.9989 这些中间值，而不是一条 0.8 秒的 `easeInOut`（e02335e2）。`PlaybackOpacityDestinationComponent` 把动画目标单独记在 entity 上：请求与它相同就跳过，非动画写入随值一起刷新目标，避免留下陈旧的目标值。

## UIKit 与 SwiftUI 的场景生命周期

- **渲染器在 UIKit 断开来源 Window Scene 之前不能跨 RealityView 根**。运行时释放所有权是必要条件而不是充分条件——它不证明 RealityKit 已经移除了异步的视频目标。**SwiftUI 根的 `onDisappear` 在 visionOS 上不是 Window 生命周期契约。**
- **新建的 WindowGroup 实例已经是 `openWindow` 的前台结果**。再去激活它的 UIKit scene 会引发系统呈现崩溃，并且不提供任何额外契约。
- **visionOS 丢弃针对 App 唯一窗口的 `dismissWindow`**，不报错也不留日志。浏览窗口因此永远不被 `dismissWindow`，也永远不被 `openWindow` 重开：播放窗口从它 push 出来，系统把它转入后台而不是销毁它（`verify_playback_surface_structure.py` 禁止执行器按窗口身份 `openWindow` 或 `dismissWindow`，push 与 dismiss 一律经由按身份路由的 capability）。
- **`WindowGroup(id:for:)` 的 `defaultValue` 每次求值都产出一个新值时，无参数的 `openWindow(id:)` 每次都开一个新窗口**。产品语义上唯一的窗口必须声明为 `Window`，由场景类型保证唯一，而不是靠每个调用点记得携带同一个值。
- **被 await 的 scene action 就是平台完成边界**。SwiftUI 不保证 ImmersiveSpace 内容的 `onDisappear` 在该 action 返回之前运行。
- **一个已消失的场景不能再接受平台请求**，但它持有的活动 lease 仍然有效，好让同一次执行经由新注册的场景根继续下去；`currentCapability` 则立刻停止暴露那个退休场景的动作。
- **同一个 `Window` 收到第二个 UIKit scene 时 SwiftUI 直接 trap**：`Fatal error: Your app was given a scene with id 'main' but the matching Window in your app body is already connected`，栈顶是 `AppSceneDelegate.makeSceneHostWindow` ← `scene(_:willConnectTo:)` ← FrontBoard `didCreateScene`，signal 5。2026-08-23 到 2026-09-06 之间播放拥有自己的 `.plain` 窗口，浏览↔播放靠先开新窗口、观察到开启、再关旧窗口的交接完成；真机（2026-09-05，11 份 `.ips`）与模拟器（2026-09-06，4 份 `.ips`）都在第二次从播放返回时命中这一帧。模拟器统一日志给出的机制：被 `dismissWindow` 关掉的播放 `Window` 的 SwiftUI 视图树在 UIKit scene 断开后仍然活着并继续响应 `onChange`，第二次打开播放窗口后就有两份 `MainView` 同时在场——`controlsVisibility`、`windowSurfaceAttached` 各出现两次，两份视图向同一个 RealityKit entity 认领（帧消失），返回时各自发一次 `openWindow(id: "main")`（同一毫秒两条 `playbackWindowHandover opened`），第二个 scene 连接即 trap。去重、销毁 session、等待 scene 断开这些补丁只是在给拆分后的窗口善后，2026-09-06 改回单窗口后全部删除。约束：浏览窗口是 App 唯一的常规 `Window`，任何第二个窗口都必须是 `WindowGroup`，而且只能靠 `pushWindow`／`dismissWindow` 成对进出，不能用 `openWindow` 与关旧窗口交接——那条交接正是把第二个 scene 交给同一个 `Window` 的路径。2026-09-09 起播放页住在 `WindowGroup(id: "player")` 里，由浏览窗口 push 出来：浏览窗口自始至终连着它唯一的那个 scene，重复 session 无从产生。旧构建在设备上留下的重复 session 由后续干净启动自然消失，若某台设备仍在启动时 trap，卸载后重装。
- **运行中的 app 再开一个窗口时，visionOS 把新窗口放在既有窗口前方并略微错开**（Apple：offsetting each additional window by a small amount），`defaultWindowPlacement` 在首个窗口上被忽略，也没有"放在原位"的位置值（`WindowPlacement.Position.replacing` 已弃用并指向 `pushWindow`）。这就是双窗口时期从播放返回后主窗口跑到右上角的来源；单窗口下主窗口从不离场，位置自然保持。`pushWindow(id:)`（visionOS 2+）把新窗口与被压入后台的窗口中心对齐、新窗口的默认尺寸取被压入窗口的尺寸、关闭或 `dismissWindow` 新窗口时旧窗口原位回来，**从一个被 push 出来的窗口再 push 是不允许的**；播放窗口从浏览窗口 push 出来，链长恒为一。进入沉浸呈现只有两步：先从播放窗口开沉浸空间，再由播放窗口把自己 dismiss，浏览窗口在沉浸淡入下原位回来；退出反着走，播放窗口不在场时由浏览窗口把它重新 push 回来。次序写在 `SpatialPlatformPlaybackWindowPolicy.actions` 给出的动作序列里（`.openImmersiveSpace`／`.dismissPlayerWindow`／`.pushPlayerWindow`），每个动作用 `issuingWindow` 说明只有哪个 scene 能发它。窗口被 push 到后台期间 `activationState == .background`，SwiftUI 根可能收到 `onDisappear`，所以"已回到前台"以 UIKit scene `foregroundActive` 为准，执行器在此时把 residency 记回 `.open`。
- **佩戴者从 window bar 关掉主窗口等同于按顶部 chrome 的返回**：播放停止、进度落盘，而不是继续在后台出声。visionOS 26 上点 x 默认**不销毁** scene：主窗口 scene 只转入 `.background`、session 保留，app 随后被挂起，`UIScene.didDisconnectNotification` 永不到来，从 Home 再点 app 图标时同一个 scene 原样回到前台（2026-09-08 真机：关窗后只有 `mainScenePhase active -> background`，再开时没有 `mainWindowScene appeared`、residency revision 不变，播放页连同视频一起回来）。所以播放窗口的 scene 一连上就把 `destructionConditions` 设为 `[.userInitiatedDismissal]`（`SpatialPlatformPlayerWindowDestructionPolicy`，`recordWindowScene` 时施加），点 x 才真的销毁 scene、发出断开通知；执行器按 `recordWindowScene` 记下的 session identifier 匹配断开，residency 记 `.closed`，只有 `.player` 这条身份再问 `SpatialPlatformPlayerWindowClosurePolicy`——播放窗口只在窗口承载播放期间存在，所以判据缩成"这次 dismiss 是不是 app 自己发的"，不是的就回调 `onPlayerWindowClosedByWearer` 停播。停播之外没有别的动作：被 push 到后台的浏览窗口由系统带回原位。浏览窗口不设销毁条件，播放期间它只是被 push 到后台，关掉再打开仍回到原来那一页；沉浸播放期间没有播放窗口，播放窗口的断开不停播。SwiftUI 根的 `onDisappear` 在窗口被 push 到后台时也会到、被销毁时又可能晚好几秒（模拟器 23 s），不能当关闭信号。这条处理在双窗口时期由 508a735e 引入、随 2f1650f7 合并为单窗口时被一并删掉，2026-09-08 按单窗口重建，2026-09-09 随播放窗口移到 `.player` 身份上。DEBUG 测试通道的 `closeMainWindow` 用 `requestSceneSessionDestruction` 销毁前台窗口 session，走同一条断开通知，供 runner 验证这条路径。
- **`windowSceneDidDisconnect` 必须先读 `playerWindowState` 再调用 `recordWindowResidency(.closed, ...)`，因为后者会把它覆写成 `.absent`**。`SpatialPlatformPlayerWindowClosurePolicy.stopsPlayback` 判断这次断开是不是 app 自己发起的，靠的正是断开前 `playerWindowState` 是否为 `.closing`——app 自己发起的 dismiss 在动作发出时就把它置为 `.closing`，佩戴者直接从 window bar 关闭则不会。函数因此先把这份值存进局部变量 `playerWindowStateBeforeDisconnect` 再覆写；颠倒这两行，`stopsPlayback` 拿到的就已经是覆写后的 `.absent`，永远读不到 `.closing`。
- **被销毁的主窗口 scene，其 SwiftUI 视图树不会被拆掉**：scene 销毁后 app 立刻挂起，SwiftUI 根的 `onDisappear` 永远不来；从 Home 再点 app 图标建出新 scene 后，旧树仍随 Observable 状态一起更新（2026-09-08 模拟器：重开后打开视频，`windowSurfaceAttached`、字幕实体、`timer-scheduled`、`windowColliderInstall` 全部成双，`mainWindowScene disappeared` 始终没有出现；真机上表现为视频帧随控件显隐整块消失再出现、docked 二级菜单 hover 忽明忽暗）。两棵树各有一个窗口 RealityView 争同一个共享视频实体、各有一套控件计时器与 ornament 高度回报。浏览窗口与播放窗口的内容各套一层 `WindowSceneGate(window:)`：它用 `windowSceneReporting` 记下自己 scene 的 session identifier，coordinator 的 `liveWindowSessionIdentifiers` 按身份记下最新连接的 scene（不在 `connectedScenes` 里的 scene 一律忽略）、断开时清空；`SpatialPlatformWindowScenePolicy.isOrphaned` 为真的树渲染 `Color.clear`，其 RealityView、ornament、计时器、residency 上报与该身份的执行器随之卸载。播放窗口被销毁后 SwiftUI 树同样不拆，所以它也必须过这道门，否则一棵旧树的 `onDisappear` 会把刚回来的窗口记成 `.closed`。卸载时 `PlaybackVideoSurface.releaseSurface` 只在实体的 parent 就是本视图记下的 RealityView 根（`hostsEntity`）时才 `removeFromParent` 并释放渲染器消费者，否则只清自己的观察者，不碰别的树正在承载的实体。
- **一份 lease 的 `currentCapability` 是"偏好的 scene 根"，不一定是浏览窗口**：只有播放窗口注册时优先，回到播放窗口后由 `preferPlayerWindowCapability` 交还。任何依赖"从哪个窗口发出"的动作都不走 `currentCapability`，而按身份取：`capability(for: .main)` 发 push，`capability(for: window)` 发这个窗口自己的 dismiss。
- **呈现表面的重挂由宿主标记触发，不由 `isActive` 触发**。视口被拆掉重建时 `isActive` 可以全程为真：readiness key 因此不变，`PlaybackVideoSurface` 的 `.task(id:)` 不重跑，表面就再也挂不上去，播放与恢复一起停在"没有画面"。真正翻动的是 `realityViewHostMarker.isActive`，它进 readiness key 才让这次重建重新武装挂载。挂载收手的四个条件——presentation 匹配、entity 匹配、entity 活着、phase settled——在一次重建之后仍可能全部为真（runtime 还记着消费者是这个 entity，entity 也还在），它们说明不了这一轮任务跑起来之后真的挂过东西。所以标记一翻动就强制先重挂一次再允许判定为 settled；其余任何 key 变化（lifecycle、formatReady、requestActive）交回簿记，那些变化没有重建任何东西，簿记是准的。
- **`register(id:actions:)` 在注册那一刻就可能把窗口设为偏好能力，不必等外显的 prefer 调用**。`makePreferred: actions.windowIdentity != nil && actions.windowIdentity != .main`：只要注册带着窗口身份且不是 `.main`，这次注册本身就让它成为偏好；播放窗口一推入就已经优先，`preferPlayerWindowCapability` 只在退出沉浸空间、把偏好交还给播放窗口这类事后重新确认的场景里才需要显式调用。
- **被 `dismissWindow` 关掉的 WindowGroup 窗口，其 SwiftUI 根的 `onDisappear` 可能晚于 UIKit scene 断开好几秒**。2026-09-06 模拟器：播放窗口的 scene 在关闭后 0.4 s 内断开（`connectedScenes` 里只剩主窗口），`onDisappear` 在 10 s 后才到，等待它的执行器在 5 s 处超时并报 conversion failed。播放窗口的离场以它自己的 scene session 从 `connectedScenes` 消失为准（`windowSceneReporting` 记下 session identifier），SwiftUI 根的 `onDisappear` 只作兜底。
- **控件自动隐藏计时器归 `PlaybackSessionModel`，不归任何视图**。它原来是主窗口 `MainView` 的 `@State Task`，随主窗口视图的 `onDisappear` 取消、靠主窗口的 `onChange` 重排，主窗口被 push 到后台或被销毁后 docked／panorama 就没有自动隐藏（2026-09-08 架构审计）。现在 `showControls` 置真与 `registerControlsInteraction` 直接在会话里排定，是否真的隐藏由 app 注入的 `controlsAutoHideContext`（播放中才隐藏）与 `canAutoHideControls`（菜单打开即 focused）决定，动画令牌也由 app 注入。四种呈现共用同一个计时器。
- **visionOS 上系统 `Menu` 内容的 `onDisappear` 在菜单关闭时不触发**（模拟器 2026-09-06 实测：`secondary menu visible=true` 之后经选项关闭、经点击外部关闭都没有 `visible=false`，只有整个 deck 消失时才有）。二级菜单的呈现标志因此不能只靠 `onDisappear` 清：选项被选中时清一次，播放表面的下一次 tap 若发现标志仍为真则只清标志不切换控件。交互碰撞体也不再因菜单呈现而移除：标志一旦滞留，碰撞体就永久消失（探针 `windowColliderInstall … hasTarget=false`），表面再也收不到 tap。重开时内容的 `onAppear` 也不再触发（2026-09-08 真机：docked 第二次打开 More 没有 `menu.more`），内容里的 `@Environment(\.isPresented)` 始终为假；UIKit 的呈现（`.popover`、`UIButton` + `UIMenu`）在 RealityView attachment 里根本不画出来（2026-09-08 模拟器与真机：willDisplay 触发、界面上没有菜单），只有 SwiftUI `Menu` 能在 Dock 里呈现。所以 More 菜单保留 SwiftUI `Menu`，呈现状态由三处事件拼出：`CircleIconMenu` 的 label 上挂 `simultaneousGesture(TapGesture)`（加内容首次 `onAppear` 兜底）报 `opened`，会话置 `windowSecondaryMenuIsPresented` 与 `isControlsFocused`（自动隐藏不跑）；行被选中报 `closedAfterSelection`，重启计时器；佩戴者在菜单开着时 pinch 视频，系统收掉菜单的同时这一下也会落到播放表面（真机 2026-09-08 01:18:49 `surface-tap-closed-secondary-menu`），`toggleControlsFromPlaybackSurface` 见标记为真即清标记并把控件一起隐藏（探针 `surface-tap-dismissed-menu-and-controls`）。菜单被别的方式关掉而没有任何一下落到表面时，标记滞留到下一次表面 tap，代价是那一下直接隐藏控件而不是切换。
- **两个窗口的玻璃都由内容自绘**。`.plain` 窗口没有系统玻璃，浏览窗口通过 `enchronWindowGlassBackground(displayMode:)`（无形状重载，container-relative 圆角，不手写窗口圆角）恒以 `.always` 保留玻璃；播放窗口用同一个修饰符，`PlayerWindowGlassPolicy` 是这条规则的唯一所有者，以 `.never` 关掉玻璃的情形有三种：`isRevealingPlayerWindow == true` 时不论呈现状态；`presentationState == .videoVisible` 时；`.hidden`／`.placeholder` 且 `hasActiveSession == true` 时——其余情形保留 `.always`。玻璃修饰符直接作用在窗口内容上：放在 `.background { Color.clear… }` 里时，玻璃的平台视图会截走其上所有纯 SwiftUI 控件的 accessibility 命中（XCUITest `isHittable == false`，真机与模拟器一致，`allowsHitTesting(false)` 无效），而 ScrollView 内的卡片、TextField、带 hover 效果的图标因为自身是平台视图不受影响；2026-09-06 用 `.plain`＋玻璃开／关两组构建二分确认。播放窗口是自己的 scene，离场时整个 scene 消失，浏览窗口的尺寸约束从未被播放改动过，所以不再有"播放根视图消失时把浏览页的尺寸下限写回"这一步。
- **播放窗口的玻璃修饰符必须与它后面的系统遮罩修饰符在源码里紧邻**。`Scripts/rules/verify_playback_surface_structure.py` 按字面文本核对 `PlayerView.swift` 里 `.enchronWindowGlassBackground(showsWindowGlass ? .always : .never)` 后紧跟 `.persistentSystemOverlays(PlayerWindowSystemOverlayPolicy.visibility(...))`，中间插入任何调用都会让这段文本匹配失败，而失败信息并不点名是这条相邻性断的。22ddad3f 修的就是这类漂移：一个玻璃探针插进了两个修饰符中间，挪到这对之后才恢复。
- **「播放期间浏览器完全消失」这一个意图，平台不允许写成一处**。`toolbarVisibility(_:for:.tabBar)` 只作用在它所挂的那个 `Tab` 的内容上，`persistentSystemOverlays` 要挂在 scene 上，其余（`opacity`／`allowsHitTesting`／`accessibilityHidden`）挂在 `WindowSceneGate` 的内容上——总共十个落点，分布在 `EnchronApp.swift`、`MainView.swift` 与 `PlayerView.swift`。把答案收拢成一个策略值只保证十处答得一致，不保证十处都答了：界面消失而 tab bar 留在原地，就是少写了四个 `Tab` 落点的样子，它曾经这样发出去过；`persistentSystemOverlays` 也曾经错误地挂在 `WindowSceneGate` 的内容上，那份外层请求对播放窗口恒答 `.automatic`（浏览器可见性策略对非 `.main` 窗口恒答假），盖掉了 `PlayerView` 自己按控件可见性发的那份，播放窗口的 window bar 因此从未跟着控件隐藏过；b8876831 把它改成只在浏览窗口的 scene 与 `PlayerView` 自己的 chrome 策略里各发一次，`WINDOW_CHROME_OWNERS` 与 `check_window_chrome_is_asked_for_once_per_window` 钉死这两处是仅有的持有者，其余产品源码出现 `persistentSystemOverlays` 就判失败。内容上的三处只有两种写法——`browserWindowContentVisibility` 与 `browserTabBarVisibility`（`Apps/Enchron/BrowserWindowVisibility.swift`），`SpatialPlatformBrowserWindowVisibilityPolicy.hidesBrowser` 只在那一个文件里被读，`for: .tabBar` 也只在那里出现一次；`Scripts/rules/verify_browser_window_visibility.py` 断言内容修饰符仍然应用全部三项、产品源码里没有第二种拼法、并逐个数 `MainView.browser` 里的每个 `Tab` 是否都带上了 tab-bar 修饰符。落点合不了，但落点的集合可以被声明和检查。

## 窗口与视频的几何

- 控制条外宽 744pt（`ControlBar.outerWidth` = 内容宽 `playerControlsContentWidth` 680pt + 两侧 `Spacing.xxl` 32pt × 2），悬在窗口下方。窗口宽度下限是 `WindowPlaybackRootView.minimumWidth` 另外写死的字面量（750pt），代码里没有一处从 `outerWidth` 推导它。
- **每一档是目标面积，不是外接盒**。外接盒自带一个形状，会饿死不共享该形状的一方——mono 源上的并排覆盖曾经因此要求一个几千点高的窗口。高度永远由宽度与视频自身比例导出，两个夹取都缩放整个矩形，窗口因此不可能与画面不一致而挣得一条空玻璃带。
- **每个能拥有窗口的表面各自声明自己的范围，没有一个在离场时恢复系统默认**。这样"一个表面消失"与"下一个出现"的先后就不会留下一个无约束的窗口。浏览页没有视频可匹配，形状固定 16:9，不欠播放任何东西；Portal 同样锁在视频的比例档上，它自己没有尺寸规则。
- **窗口视频网格与 Window 的 SwiftUI 平面共面**，并带 `ModelSortGroup.planarUIInline`——按 z 排序而不是按视图树。画在视频之上的 chrome 因此需要一个向前的位移（`coincidentChromeDepth = .ulpOfOne`，Apple `PlanarUIPlacement` 示例的写法），否则网格赢下平局、chrome 永不出现。**顶部 chrome 的衬托不能是一块满宽的带**，原因各不相同但都封死了："`ContainerRelativeShape` 推出的各角半径在真机上左右不对称，即使挂在窗口根上；SwiftUI 材质采样不到 RealityKit 视频；RealityView 里加的任何网格拿不到圆角——只有 VideoPlayerComponent 自己画的屏幕有；`.plain` 窗口对不前移的 SwiftUI 内容也不做圆角裁切；手写半径又违反"窗口圆角由系统管理"。阴影（模糊盘被控件框裁成方块）和另加一圈白描边也都被否。最终答案是**按钮自己的表面**：`CircleIconLabel` 与 Files 页是同一个组件、同一条 `chromeBorder` 0.5pt 描边，表面统一为 `.ultraThickMaterial`（`enchronButtonSurface`）。
- **字幕平面不写深度，并且自己声明排序组**。`UnlitMaterial(texture:)` 默认 `writesDepth == true`，透明纹素也在平面的 z 上写深度；字幕实体又是视频实体的子实体，而 `ModelSortGroupComponent` 不随父实体继承——子实体上没有就是没有——平面与视频网格谁先画由渲染器决定。平面先画时整块矩形里的视频被深度测试拒绝，透出窗口背景：2026-09-06 实测暂停、控件升起、字幕上移时字幕后面出现深灰或棕色方块（颜色随环境变）。因此 `PlaybackSubtitleSurface` 的材质 `writesDepth = false`，窗口呈现里字幕实体带 `ModelSortGroupComponent(.planarUIInline, order: subtitleSortOrder)` 排在视频之后；纯粹的位置变化只改 `position`，网格与材质只在贴图对象或尺寸变化时重建。断言在 `PlaybackPresentationTests`：`subtitleSurfaceBlendsOverTheVideoWithoutOwningDepth`。
- **播放表面的按钮语义挂在交互碰撞体上，标识符挂在 SwiftUI 容器上**。`AccessibilityComponent` 没有 `identifier` 属性（2026-09-07 编译确认），而 XCUITest 只按标识符寻址，因此 `PlayerUI-window-playback-surface` 落在窗口 RealityView 的 `.accessibilityElement(children: .contain)` 容器上；容器自身不是元素，合成点击落到容器中心就是落到碰撞体上。`PlaybackSurfaceAccessibility.install(on:)` 给 window／docked 碰撞体与 panorama 每块面板写 `label`、`traits = [.button]`、`systemActions = [.activate]`；视频实体不带辅助功能组件——它没有碰撞体，元素框会退化成窗口左上角的一个方块。`AccessibilityEvents.Activate` 在场景级订阅，再用 `PlaybackSurfaceInputOwnership.acceptsSpatialTapTarget` 过滤，与空间点击走同一套归属判定。
- **沉浸 RealityView 不会因字幕帧变化而重跑 update**。窗口表面在 `update:` 闭包里同步读 `activeSubtitleFrame`，SwiftUI 因此追踪它；沉浸视图把整个更新排进 `realityViewUpdateScheduler` 的异步任务，读发生在闭包之外，帧变化不触发任何重跑——2026-09-07 实测 docked 只画进入时那一帧。`ImmersiveSpaceView` 因此显式 `.onChange(of: activeSubtitleFrame?.changeIdentifier)` 调 `refreshSubtitleSurface()`，并只在 `rendererConsumerPresentation` 是自己时写，避免与窗口视图的字幕实体同时挂到共享视频实体上。
- **Portal 与 panorama 的字幕钉在可见区域的下方居中，不跟源画布的位置走**。Portal 只显示 180° 内容的中心裁切，源在画布上给的位置可能落在裁切之外；`PlaybackSubtitlePlacement.pinsToLowerCenter` 对这两种呈现忽略 `contentX`／`contentY`，水平居中、底边留屏高的 `pinnedBottomFraction`（8%），尺寸仍按画布比例换算。Window 与 docked 保留源位置。
- **Panorama 的字幕缓动跟随视线，不锁死在头上**。刚性 `AnchorEntity(.head)` 会把头部的微小抖动原样传给字幕，佩戴者报告眩晕（2026-09-07 真机）。`PanoramaSubtitleFollower` 改用与控件 attachment 相同的 `WorldTrackingProvider.queryDeviceAnchor`，每帧（`SceneEvents.Update`）取头部朝向，交给纯函数 `LazyGazeFollow`：目标与当前朝向差在 8° 死区内不动；越过死区进入追赶，按时间常数 0.4 s 指数逼近，差小于 0.75° 时停下。位置直接跟头部平移。控件升起后字幕**吸附到控件所在的平面上**：头部朝向与控件方向的**偏航**差 15° 以内进入停靠、超过 25° 才释放（滞回）；只比偏航，因为控件本来就放在视线下方 22°（定这条规则时是 17°），比俯仰会让正视前方时永远进不了停靠（2026-09-07 真机），释放后跟随头部，转回 15° 以内重新吸附。停靠时字幕保持自由态的局部布局不变，`dockedRootTransform` 反解出根实体的目标 transform：朝向取控件的朝向，按控件距离÷虚拟屏距离缩放保持角尺寸，平移使钉住的字幕底边落在控件平面上、控件中心上方 `dockedSubtitleBottomAboveControlsMeters`（0.10 m）。停靠与释放之间根实体仍按指数缓动，但时间常数按**统一速度**在切换瞬间算出：字幕屏中心的世界位移 ÷ `dockTransitionSpeedMetersPerSecond`（6.3 m/s，释放位移约 1.57 m 对应时间常数 0.25 s，2026-09-07 佩戴者定的手感），下限 `minimumDockTransitionSeconds`（0.12 s）。同一时间常数下位移小的一段会显得拖，佩戴者反馈吸附拖而释放正好（2026-09-07 真机），统一速度而不是统一时长。**过渡路径向上拱起** `dockArcHeightMeters`（0.35 m，正弦包络）：自由屏在 2.2 m、低 14°，控件面板占据视线下方约 11°–23°（该次实测时控件偏移为低 0.22 m，现为低 0.28 m，整段再下移约 4°），直线路径前半段整个藏在面板后面，吸附显得比释放久得多其实是被挡住了（2026-09-07 真机，原地不转头可稳定复现）；拱起后字幕全程在面板上方可见。字幕因此是从原位置**移动**到停靠位置，没有局部布局跳变；停靠与否不再靠 `reservedBottomFraction` 抬升。断言在 `PlaybackPresentationStateTests.subtitleSurfaceBlendsOverTheVideoWithoutOwningDepth`。字幕平面挂在 follower 根实体下，用 `panoramaScreenSize`（16:9，高 0.9 m）与 `panoramaScreenCenter`（前方 2.2 m、低 0.55 m）：同样角尺寸的平面放在 3 m 处会因深度线索显得很大，2026-09-07 佩戴者反馈偏大偏高后收近、压低。停靠与脱离之间根实体的位置、朝向、缩放都按同一时间常数缓动，不瞬移。追赶数学的断言在 `PlaybackPresentationStateTests.lazyGazeFollowHoldsInsideTheDeadZoneAndEasesBeyondIt`。
- **控件升起时字幕按实测遮挡抬升，不用常数**。窗口与 portal 的 PlayerPanel 是 `.scene(.bottom)` 的 ornament，中心压在窗口下边，上半覆盖画面；覆盖的**点数**基本恒定，窗口高度却随呈现变化，原先的 0.32 常数在 portal 里把字幕抬得过高。现在 `MainView` 量 ornament 高度、`WindowPlaybackRootView` 量表面高度，`PlaybackWindowChromeOcclusion.bottomFraction` = (ornament 高 × 0.5 + 12 pt) ÷ 表面高，`PlaybackVideoSurface` 在控件可见时以它为 `reservedBottomFraction`。**同一个比例也从交互碰撞体上切掉**：碰撞体原来只避开顶部 chrome 条，portal 下 ornament 压住的画面底部仍归碰撞体，注视捏合进度条会被碰撞体接走、变成一次 surface toggle 把控件关掉（2026-09-07 真机）；`interactionRegion` 现在同时减去 `bottomFraction`，控件隐藏时 `bottomFraction` 为 0，底部恢复为可点的画面。Panorama 的控件是头前 0.7 m、低 0.28 m 的 world-locked attachment（摆放只继承偏航，见「沉浸空间的几何与输入」），字幕的抬升由上一条的共面停靠承担。
- **Portal 需要它的 Window scene 里有空间厚度**。取值是 SwiftUI 场景单位，对齐 Apple 沉浸媒体 PlayerWindow 契约；零厚度的宿主会让组件停在 loading。

## 饥饿指示画在画面上

- **播放中饥饿与 seek（`loadingStage == .starved` 或 `.seeking`）只叠加转圈与读速率，不清空画面**。窗口与 Portal 由主窗口画布的 ZStack 叠加 `LoadingSpinner`，并像控件一样抬高 `coincidentChromeDepth`：不抬高时它与视频网格共面，保持住的那一帧会盖住它（2026-09-09 真机截图）。视频表面本身不看加载态（`windowSurfaceIsActive` 只读 residency 与绑定策略），所以转圈画在 seek 保持住的那一帧之上，而不是换掉它。Dock 与 Panorama 由 `ImmersiveSpaceView` 的第二个 RealityView 附件承担，挂在字幕所在的父实体上：Dock 在屏幕中心前 2.5 cm，Panorama 在字幕跟随根正前 2.2 m；只在饥饿或 seek 且无转场时启用，启用写入与其他实体一样进探针日志。打开阶段仍是原来的整窗加载。
- **seek 的指示要等 `PlaybackSeekIndicationDelay.duration = 0.5 s` 才出现**。seek 停住时间线并作废看门狗，饥饿观测因此不可能在 seek 期间到达，`.seeking` 是四个呈现共用的唯一来源。发布挂在 runtime 已有的 seek 代次上：`seek` 与 `skip` 起一个去抖任务，下一次 seek 取消它并重新计时，任务在发布前复核代次与 `seekIsInProgress`，seek 完成、失败或被取代时由该代次的收尾清除。半秒的界是给人看的——本地 seek 在几十毫秒内落定，画一下就消失的转圈比不画更糟；慢驱动器上的 seek 现在按进展而不是固定五秒收场（见 `docs/PLAYBACK_ENGINE_CONSTRAINTS.md`），因此指示要能存活到 seek 真正结束。seek 期间到达的饥饿观测被丢弃，`endSeek` 只从 `.seeking` 回到 `.none`，所以完成的 seek 不会清掉它之后开始的饥饿。断言见 `aSeekLongerThanTheIndicationDelayShowsTheSeekingStageInEveryPresentation`、`aSeekShorterThanTheIndicationDelayShowsNothing`、`aCompletedSeekClearsTheSeekingStage`、`aSupersedingSeekRestartsTheIndicationDelay`（`Tests/PlaybackFeaturePackageTests/PlaybackLoadingStateTests.swift`）与 `immersiveStallIndicatorShowsStarvationAndSeeking`（`Tests/PlaybackPresentationTests/PlaybackPresentationStateTests.swift`）。

## 沉浸空间的几何与输入

- **Immersive Space 的原点在佩戴者脚下的地板上**。authored anchor 携带佩戴者的名义眼高，距离与仰角把屏幕放在以该点为中心的球面上。
- **交互壳必须够到远高于站立眼高、也远出常规房间尺度移动的范围**，佩戴者能占据的每一个眼位都留在壳内、留在每一块面板之外。面板做得薄，是为了让一条离开壳的注视射线恰好穿过其中一块。180° 投影只拥有前半球，360° 拥有所有方向。
- **控件 deck 的摆放只继承佩戴者的偏航**。`ImmersivePlaybackControlsAttachmentController` 原先把设备锚的整个 `originFromAnchorTransform` 乘上一个纯平移偏移，deck 因此连头部的俯仰与翻滚一起抄下来并锁进世界：佩戴者歪着头召唤控件，deck 就以同样的倾角悬在那里；抬头召唤则 deck 被推到眼睛上方。`ImmersivePlaybackControlsPlacementGeometry` 从头部前向量在 XZ 平面上的投影解出偏航（前向量退化——正看天顶或脚下——时改用头部上向量），只以该偏航绕世界 Y 轴建旋转，平移偏移在这个偏航坐标系里施加：deck 永远水平正视佩戴者所朝的那一面，垂直偏移沿世界 Y 轴量，与召唤那一刻的抬头低头无关。摆放仍然只发生在控件可见的上升沿，此后世界锁定，deck 不跟随转头。偏移是头前 0.7 m、低 0.28 m，即视线下方 21.8°：佩戴者要求在不必低头的前提下把 deck 压离视野中心，原先的低 0.22 m（17.4°）太靠上，再低于 23° 就开始需要低头。断言在 `WindowPlaybackPageGeometryTests.immersiveControlsPlacementKeepsYawOnly` 与 `immersiveControlsPlacementMeasuresHeightInWorldSpace`，结构由 `Scripts/rules/verify_playback_surface_structure.py` 把关。
- **透明 SwiftUI attachment 接不到真实注视**。2026-08-10 的佩戴者实测里 8/8 次捏合都未命中它。Apple 自己的沉浸媒体示例用一个带 input target 的**不可见碰撞实体**接收召唤捏合，本产品照此办理。
- `PlaybackSurfacePlacement.dock` 用 `look(at:from:relativeTo:)`，其默认前向是本地 -Z，而 `VideoPlayerComponent` 画面的可见面是本地 +Z；因此 look 的目标取佩戴者的反方向，让 +Z 朝向佩戴者。让 -Z 朝向佩戴者会呈现画面的背面，左右镜像。子碰撞体沿 +Z 正偏移才在视频前面，与窗口呈现一致。
- **仰卧注视下的轴约定**：注视朝前时世界 Y 轴向上，视线向下是 -Z（朝向胸口）。`WindowPlaybackPageGeometryTests.immersiveControlsPlacementFollowsSupineGaze` 的三个平移断言按这条读——水平分量恒为零，Y 是世界高度减去前向偏移，Z 是垂直偏移；deck 的上向量（本地 +Y 经摆放旋转后）因此落在世界 +Z 上。

## 呈现转换的所有权与次序

- **同一沉浸呈现内换渲染器（docked 里选集，即换媒体、重开技术会话）会原地铸造新实体，退役实体必须由沉浸表面当场释放**。实体仓库在渲染器变化时把旧实体记为 `departingEntity`（跨 RealityView 交接要靠它），窗口表面在没有转换时立刻 `content.remove` 并 `releaseDepartingEntity`，沉浸表面此前没有这一步：旧的 docked 屏幕带着停掉的视频组件留在新屏幕同一位置（两块屏叠着闪），退出时 `hostedEntity(for: docked, during: docked→window)` 又把这个退役实体当离场实体交出去，`claim outcome=busy` → `rendererReleaseUnavailable` → 转换失败、播放被拆（2026-09-08 真机 01:19:32；模拟器 docked 选集后 exitSpatial 同样复现）。`ImmersiveSpaceView.update` 现在与窗口表面同样处理（探针 `rendererOwnership.departingReleased scope=immersiveSpace`），panorama 走同一个函数。换字幕轨、换音轨、加载外挂字幕只落在当前 driver 上（`requireActiveDriver().selectAudioTrack / selectSubtitleTrack / addExternalSubtitleSource`），不换渲染器、不碰屏幕实体。
- **两个宿主接管共享视频实体的顺序只有一份：`PlaybackVideoSurfaceReconciler.acquire`**（取／铸实体 → 释放原地离场实体 → 拓扑写权限门 → 认领渲染器消费者），窗口与沉浸宿主各自只保留几何、锚点、交互面与对结果的处置；规则脚本钉住两侧各调用一次且不再自行 `releaseDepartingEntity`。沉浸侧的观看模式重请求在 3 秒窗口耗尽后原来静默放弃，现在以证据级探针 `modeRequestRetry exhausted …` 报一次（想要／实际的沉浸与空间模式、观察到的内容类型），不弹错误，方便真机回捞定位 panorama 黑屏这类“画面不对但没有报错”的情况。
- **运行时 attachment 属于转换的目标呈现**（没有转换在跑时就是已落定的那个）。离场的窗口表面在主窗口关闭完成前仍然挂载，如果在替换技术会话上把它重新 attach，就等于从沉浸表面手里把 attachment 抢回来，此后 settlement 永远无法提交，整次打开在 executor 的期限上回滚。
- **一次呈现内部的技术会话替换没有 Scene 消失来退休上一个视频实体**。把它留在原位，它的 `VideoPlayerComponent` 会继续把最后一帧喂在新表面之上；而每个被保留的渲染器都让自己的解码管线在 `mediaplaybackd` 里活着，直到该守护进程触到内存上限。
- **consumer record 必须携带 renderer epoch**。记录以 Entity 身份为键，而 entity store 在渲染器被替换时铸造新 Entity，因此来自更早 epoch 的记录指向一个再也无法呈现的 Entity。不带 epoch 时这种记录会拒绝新渲染器上的每一次认领、表面永远重试，因为唯一能清除它的代码被那个已经被替换掉的身份守卫着。
- **目标表面通常自己启动 cutover**，就在它证明自己的像素带着当前身份的那一刻，这是退出快的原因。executor 侧的 settlement 是同一份证明晚一个来回到达，用于表面**没得到机会**的情况（没有后续 RealityView 更新，或转换在它脚下变了）。
- **进入沉浸空间要把播放器窗口收掉，而且必须在进入的动作序列里收，不能等空间出过一帧**。判据是失败率，不是耗时：放在进入里（`openImmersiveSpace` 之后 `dismissPlayerWindow`）两轮共 18 个循环 0 次失败；移到视觉切换之后，`spatialPlaybackSurfaceUnavailable` 的失败进入立刻回来，9 个循环里 2 次——窗口表面在整段进入里还挂着，就会抢在 docked 之前认领新铸的实体，正是修复前那条竞态（2026-09-10 模拟器）。**耗时上两种次序没有差别**：第一轮验收量到进入里收窗口要 14–19 s，看着像是这个次序的代价，但同一份代码在机器空闲时复测是 5–8 s、中位数 7 s，与移到切换之后的 4–8 s 同档；那一轮是与两个 xcodebuild 和一遍门禁同时跑的，14–19 s 是机器争用，不是产品行为。**在这台机器上量模拟器的时序，必须让别的构建先停下来。**
- **`modeRequestRetry` 在 docked 期间是自由运行的 8 秒定时器**（+14、22、30、38…，一次 55 秒的停留会打出 6 条），与进入成功与否无关。只有当一次进入本身跑得够久、跨过了这个定时器，重试才会出现在进入区间里；把它当成进入被打断的信号会归错因。
- **沉浸进入失败必须显式要求把播放器窗口推回来**。`recordImmersiveSpaceResidency(.open)` 在空间一 appear 就把 residency 记成 `.playing(.immersiveSpace)`，此后 `normalizeWindowTransition` 算出的是 `returnsToPlayer: false`，也就是「不要窗口」；而这时播放器窗口已经在进入序列里被 dismiss 掉了，佩戴者会落到一个既没有空间也没有窗口的地方。`enterImmersivePlayback` 的每一条失败路径因此走 `immersiveEntryFailureWindowTransition`（固定 `returnsToPlayer: true`），不再问 residency。
- **窗口表面在沉浸进入时还挂着，就会抢走新渲染器的实体，退出因此有一定概率交不回来**。2026-09-10 模拟器，6 个有效 dock 往返里 2 次退出后窗口空白。探针里判别式在**进入**那一刻：健康的进入只有两行，`rendererOwnership.entityMint` 打 `presentation=docked` 并直接认领新铸的实体；失败的进入 mint 打 `presentation=window`，先由 window 认领退役实体、再释放、再把新实体交给 docked，随后跟着 `modeRequestRetry` 与 `spatialFirstFrameUpdateDrive event=stopped:surfaceNoLongerViable`。退出于是以 `spatialPlaybackSurfaceUnavailable` 回滚，窗口停在 `corePresentationPhase=surfaceAttached`、`displayedPixel=false`、`error=surfaceAttachmentFailed`，画面位置继续推进但一帧不显示，并弹出「video surface could not be attached」告警；佩戴者唯一的出路是关掉这个窗口，回到 browser 重放。判别要看 `lastExecutionResolution`，`conversionDiagnostic` 是黏的，第一次失败之后健康退出也照样带着那段失败文本。同一批证据把「视频开了两份」缩到很窄：docked 稳态下只有一个 renderer consumer，enablement 链 59 次全是 `EnchronVideo.docked`。要说清楚边界——这读的是产品自己的所有权账本，不是 GPU 或解码器负载，测不出真实开销；失败的进入里两个实体确实同时活着（退役的那个先被 window 认领再释放），只是先后接力而非并行出画。能确定的是留下来的那个窗口 scene 与它的 RealityView 宿主是真实成本，「第二条解码管线」没有证据支持。
- **每一次 push／dismiss 都把两个窗口一起往下挪约一个固定量，同一进程内累积**。2026-09-10 模拟器实测：只做「开片—返回」的 push／dismiss，不开任何空间，播放器窗口顶边在 3840×2160 渲染里从 716 走到 1114，五次交换共 497 px，每次 99.4 px，稳定到 ±1 px；100→99→98 的递减是同一个世界坐标位移在窗口下降时的透视投影，不是量在变。**browser 自己也同步下移同样的量**（600→1096），所以这不是「caller 不动、被 push 的窗口在飘」，两个窗口是一起走的。一次沉浸往返与一次普通 push／dismiss 完全等价，只贡献一次交换（+97／+100／+100），沉浸空间本身不参与；沉浸屏在相邻循环之间纹丝不动（904／903）。`relaunch` 把两个窗口精确复位到起点（600／716），累加器因此在进程内、不落盘。机制早于「进入沉浸时收掉播放器窗口」的改动——push／dismiss 成对出现就会累加，开片／返回这条路一直如此——但用户看到的量变了：旧实现每次 dock 往返 0 次交换，新实现 1 次，所以一次播放里连做 9 次 dock 往返会把窗口走低约 900 px（acceptance 的 c9）。旧实现在 dock 往返上从未被测过。全部结论只来自模拟器。尚未定位到产品侧的成因，也尚未修复。

- **browser 的隐身条件挂在 residency 上，代价是 push 失败时没有兜底**。`SpatialPlatformBrowserWindowVisibilityPolicy` 对任何 `.playing` 与 `.closing` 都隐身；而窗口播放的那次 push 是 `applyPlaybackResidency` 里发出去就不管的（`issuePushedWindow`），所以 `noBrowserCapability`、或者窗口一直停在 `.opening` 不出现，residency 会卡在 `.playing(.window)`，browser 不画、不接输入、不出 bar，没有任何东西把它救回来——关闭预算只在离开播放时才跑。改动之前 browser 是「播放器窗口不在就显示」，这类失败会自己露出来。目前没有可注入的失败通道来复现它，所以只记录不修。

- **播放结束之后再进入沉浸空间会走进一个没有出口的失败态**。`lifecycle=Ended` 时 `pixels` 永远不会变真，settlement 等满三次 8 秒定时器（约 34 s）后判失败，失败路径把播放器窗口推回来并带回完整 chrome，但**既不弹「Playback Error」也不出 `PlayerUI-loadFailure-*`**，佩戴者只看到一个没有画面、没有任何错误提示的窗口；同时 `PlayerUI-TopAction-dock` 掉出层级，这个状态再也进不去空间（2026-09-10 模拟器，`lastVideoPTS=599.85` 时驱动的一次进入）。尚未修复。

- **从空间回到主窗口：窗口表面只在窗口可见后才 attach，视频一到就整体出现**。播放窗口一 dismiss，系统就开始还原主窗口（scene 从 background 经 inactive 到 active 约 1–2 s）；窗口 RealityView 在 `background` 期间不跑 update、不 attach（2026-09-07 真机：允许绑定后等 1.5 s，`windowRevealReadiness … attached=none`），所以"先在后台备好视频再放窗口回来"做不到，executor 允许目标绑定后立即 dismiss 播放窗口。attach 与像素证明落在 `background -> inactive` 之后的同一秒内、早于 `active`，cutover 由表面在像素证明时启动，视频实体直接置 1（`animatesWindowVideoEntity` 为假，不淡入），chrome 从 cutover 起挂载（`PlayerWindowChromeHostingPolicy`，deck 在 transition 结束前不接输入），主窗口 glass 全程不显示（布尔值由 `SpatialPlatformImmersiveExitWindowRevealPolicy.isRevealingMainWindow` 算出，`PlayerWindowGlassPolicy` 消费它）；佩戴者看到的是还原动画带着视频和控件一起进来。**App 自己请求的 panorama 退出不再做 portal viewport refresh**：同尺寸的 `requestGeometryUpdate` 在窗口回到前台后会让窗口内容再淡出淡入一次，看起来像窗口又出现了一次（2026-09-07 真机，docked→window 没有这一步也没有这一下）；这条边上 attach 发生在窗口可见之后、布局有效，cb63b07e 针对的灰窗只在系统关闭空间的 collapse 路径上出现，refresh 只保留给 `collapseImmersivePlayback(.panoramic)`。docked 的退出原先多等 `sourceFadeDuration`（2 s）淡出，这一步已删；常量本身没删——`PlaybackPresentationChrome.swift:35` 仍声明它，`animation(for:)`（`:115-121`）在目标 opacity 归零时仍用它做动画时长——只是产品代码里已经没有路径把它接到 docked 退出上，直接引用这个常量的只剩测试。曾用渲染器最后显示的像素做一张 SwiftUI 静帧桥接（7d80aba1）：静帧是直角矩形、贴在窗口平面，而 portal 视频在圆角门内、位于窗口平面之后，两者不可能重合，佩戴者看到的是一张图片先出现再消失、窗口才出现（2026-09-07 真机），故删除，宁可透明也不放不属于窗口的画面。离场的球面／屏幕连同最后一帧留在空间里直到空间关闭（释放所有权时只摘交互面，不再 `removeFromParent`），关闭动画收走的是画面而不是空场景。
- **播放中的 transfer 必须先推进替换渲染器**，RealityKit 才能在每一种呈现里确认第一个显示像素；暂停的 transfer 没有成功后意图，保持暂停。
- **等待必须有界**。调用方在整个等待期间持有平台执行 lease，无界等待会让这个 lease 被永远占住，此后每一个空间请求都被拒绝直到应用重启。界限取得宽，是因为高分辨率全景启动本来就慢——但没落定的表面不是"启动慢"，是卡住了。
- **两处等系统窗口生命周期状态变化的界限不共享同一个常量**。`windowLifecycleConfirmationTimeout`（push 窗口、等它前台化）取 5 秒；`dismissEnvironmentCardIfNeeded` 等 SenseZone 音量关闭用的是硬编码的 `.seconds(10)`（`SpatialPlatformEffectExecutor.swift:1617`）。这处 10 秒从这个函数第一次出现起就是这个值，代码与提交历史都没有说明为什么它是前者的两倍。

## 主窗口列在哪些呈现里还在

- **window 与 portal 保留主窗口列，panorama 与 docked 不保留**。窗口 chrome 只能在这两种呈现里由表面点击召唤，格式菜单也只在召唤之后才接受点击；沉浸式呈现下窗口已经空了，表面点击没有落点。见 `Scripts/verification/playback_transition_stress.py`。
- **承载 portal RealityView 的视图不能在可见期间翻转 `allowsHitTesting`**。从 panorama 返回 portal 时，窗口带着视频随系统还原动画出现后约 0.2 s 视频整块消失、再花 0.7 s 淡回来，ornament 不动，暂停与播放中都一样；docked→window 看不出来。真机连拍（`screenshotBurst`，2026-09-07）把消失时刻钉在 transition 提交那一帧：提交延后 3 s 它就跟着延后 3 s，scene 变 active 时什么都不发生；把承载 RealityView 的 `windowPlayback` 上随 `windowPlaybackAcceptsInput` 翻转的 `.allowsHitTesting` 改成常量后，消失彻底不见。visionOS 在 `allowsHitTesting` 变化时重建该视图的合成层，flat 视频原样重画，portal 的沉浸渲染要重新淡入。现在 `allowsHitTesting` 只跟随 `windowPlaybackOpacity > 0`（沉浸态下窗口不可见时才关），转场期间的表面点击改由 `PlaybackSessionModel.toggleControlsFromPlaybackSurface` 在 `presentationTransition != nil` 时忽略。deck ornament 同理：它的 `allowsHitTesting` 只跟随自己的 opacity，不再在提交时随 transition 翻转。连拍还显示控件条在提交那一帧本身是连续的，它唯一的可见变化是播放键在 +2.3 s 从 ▶ 变 ⏸——播放意图原先要等主窗口回到前台才恢复，窗口出现完了才开始播。现在 executor 在播放窗口 dismiss、替换会话 rebase 完成（attach 之后、窗口还在淡入）就恢复播放意图，再等前台；窗口露出时已经在播。同一次排查排除的候选（都有连拍为证，均不改变现象）：还原前先在后台备好视频（后台 RealityView 不 attach）、portal viewport refresh、RealityKit 的 immersive viewing mode 过渡（不发事件）、push 前清空窗口让系统快照为空、提前退休离场渲染器图、提前摘掉全景实体的沉浸组件。
- **浏览窗口的尺寸约束是它自己 scene 上的常量，播放不再读写它**。`MainView.body` 直接挂 `.browserWindowGeometry(onWindowSceneChange:)`（`WindowPlaybackRootView.swift:105-121`），对浏览窗口的 scene 请求 `BrowserWindowLayout.minimumSize`／`maximumSize`，与播放呈现或 residency 无关。播放页现在住在它自己的 `WindowGroup(id: "player")` 里，离场时随 scene 一起消失；原先"记下播放前尺寸、卸载时按 `BrowserWindowLayout.restoredSize(remembering:)` 恢复，否则回默认尺寸"的那一整套——连同判断沉浸空间是否已关闭的 `BrowserWindowGeometryPolicy.shouldRequestDefaultSize`——随 f1ccfd42 把播放单独开成一扇窗口一起删除。
- **播放页在整个播放请求期间无条件挂载，沉浸态下只是 opacity 0**。原先 `showsWindowPlayback` 在主窗口内、落定为 panorama／docked 时为假，`WindowPlaybackRootView` 被卸载、浏览器（`Color.clear`）顶上；从空间返回时根视图重建，`@State` 归零，旧的 viewport refresh revision 被当作新请求再发一次同尺寸 `requestGeometryUpdate`，`onDisappear` 的 freeform 几何又在还原动画里被 aspect-lock 覆盖（2026-09-07 真机：还原期间 revision 4 重发）。播放页现在住在它自己的 `WindowGroup(id: "player")` 里：`PlayerView.primaryContent`（`Apps/Enchron/PlayerView.swift:216-241`）无条件挂载 `windowPlayback`，挂载与否只取决于这个 WindowGroup 有没有被 push，不再有 view 内部的布尔开关；打开失败的播放页带着重试弹窗留在原地（residency 是页，不是会话存活），`windowSceneHostOpacity` 在落定沉浸态下给 0，`allowsHitTesting` 与 `accessibilityHidden` 一起关掉，辅助功能树里没有 `PlayerUI-window-control-plane`，与卸载时一致。托管呈现取落定呈现所在家族的主窗口呈现（panorama→portal、docked→window），几何策略在进入空间时就切到返回后的那套，返回时不再改。`PlaybackPresentationRendererBindingPolicy.shouldBindRenderer` 多一个 `settledPresentation`：没有转换时只在托管呈现等于落定呈现才绑定，否则常驻的窗口表面会在 panorama 期间认领渲染器。
- **投影只在主窗口列里改变，空间格子只有『退出』这一条边，退出可以跨内容族**。docked→portal 与 panorama→window 是合法的 `exitImmersive`，平台效应 `exitImmersivePlayback(family)` 按目标族落到主窗口的对应格子；window→panorama 与 portal→docked 仍然非法，进入空间永远是佩戴者在主窗口列里的显式动作。从 panorama 直接 apply-flat 是一条同时改投影与改呈现的对角边。见 `Scripts/verification/playback_transition_stress.py`。
- **换片时由内容族决定去向，不替佩戴者重进空间**。`EffectiveMediaFormatPresentationResolver` 比较新片的内容族与当前呈现的内容族：同族原地换，docked 换平面片、panorama 换全景片都留在空间里；异族时请求该族的主窗口格子，在空间里就是一次跨族退出，在主窗口列里就是投影交换。自动连播走同一条规则。2026-09-08 真机：docked 内选 180 集黑屏有声，是旧 resolver 对空间呈现一律返回 `unchanged`、新片被塞进平面 dock 屏的结果。
- **被来源信令标注为全景的内容，在有人请求 panorama 之前落在 portal**。只把 window 当作合法落点，集合里每一个空间片都会走到超时。见 `Scripts/verification/playback_open_sweep.py`。

## 注视输入下的控件判定

注视解析到的落点比光标粗得多，窗口播放控件的几处判定都由此而来：

- **一个目标里面不要再放小目标**。播放信息井是可点开的整块，井里再放一个小控件，它会把本该属于井的点击接走。井内元素因此只作指示，不接受输入。
- **注视点亮之处必须就是捏合起始之处**。scrubber 的可见抬升贴着画出来的拇指，而外层那圈胶囊才是接住手的范围；它与 `isThumbHit` 用同一几何，因此凡是注视落下并点亮控件的地方，捏合都能开始一次拖动。
- **水平轨道只测水平距离**。手势挂在整条 strip 上，起始位置在纵向已经通过了 strip 的 interaction 形状；决定"佩戴者是不是要拖这个 scrubber"的轴只有沿轨道那一个。
- **松手之后 scrubber 锁存在目标值上**。`onSeek` 之后运行时的位置是异步追上来的，锁存期内拇指钉住目标，否则会出现"跳回旧位、再闪到目标"。运行时位置进入容差（`pendingTargetSettleToleranceSeconds`，0.25 s）即释放，另一条释放路径是 `controlsVisible` 变假。
- **拖动开始的那一帧显示的是实时位置，提交的是手势位置**。面板的本地进度值只在拖动期间才有意义；每次控件重新显示面板状态都会重建，`beginScrubbing` 若不用实时位置初始化它，第一帧就画出初始值（曾是 0.45，即"先跳到中间"），而只有起止两次采样的拖动会把这个陈旧值提交成 seek 目标。`PlaybackSeekPresentation.ScrubDrag` 记住起点的进度与横坐标，拖动中的显示与松手时的提交都由当前横坐标从它推导。断言在 `PlaybackPresentationStateTests`：`scrubDragRendersAndCommitsTheGesture`。
- **展开时间轴的唯一事实是 `contentWidth = duration × pps`**。拖拽极限、标尺与胶片末端全部以它为准；单独截短整体会与拖拽极限脱节，而且在最小缩放下一格约合数十秒，白白丢掉可拖范围。

## 窗口控件的自动隐藏

- **窗口播放控件在一段空闲之后自动隐藏，这段窗口的长度由启动参数给定**。一个要证明"打开菜单会钉住控件"的场景必须把它压到自己的探测点之前，否则读到的 controls=shown 由启动参数保证，与产品无关。见 `Scripts/verification/regression_preparation_adapter.py`。

## 探针文件的写入纪律

诊断探针写在应用容器里，被证据链读取，因此它的体积是一条真实约束：

- **每种日志一个去重槽**。把每帧的表面事实与 attach 探针共用一个槽，会让两者都无法重复自己的上一个值，于是 attach 探针每帧触发并把探针文件冲爆。
- **时钟与计数器字段不能进去重签名**。它们每帧前进，会让每一条 settlement 行都独一无二，文件增长快到中途卡死容器拷贝。
- **沉浸打开的竞态只表现为两次 attach 的先后**，因此它必须进探针文件，并按技术会话去重。
- **证据保留只属于 harness 会话**。evidence 记录不参与压缩，harness 用 `evidenceSession` 换会话时才整体清空；从 Home 手动启动的进程没有这一步，文件被上一次 harness 的证据填满后，手动会话的每一条记录（含 evidence）都被静默丢弃。2026-09-05 真机上 196 468 B 的文件对 196 608 B 上限就是这样让一整天的手动验收没有留下任何探针。因此没有 `ENCHRON_TEST_CHANNEL=1`（只有 XCUITest runner 设置它）的进程把加载到的记录降为 diagnostic、会话置空，压缩可以腾出空间；harness 进程保持原语义。见 `Tests/EnchronApp/DebugProbeJournalTests.swift`。

## 领域模型为何这样切分

- **Media Format 的来源信令事实不可变**。用户的解释永远不改写它们，Automatic 解析回这份事实而不是制造一个平面回退。会话面向的解释是单一值，呈现策略消费它时不再回读可变的运行时字段。
- **playback-mode family 与 Media Format 分开持久化**：投影与立体解释留在 `formatPreference` 里。
- **Dolby Vision 的 profile 与 layers 分开存**。`HDRType` 只能命名一种动态范围，而 Profile 7 的来源同时有两个答案：它是 Dolby Vision，而到达佩戴者的是它的基础层。layers 决定回退，profile 号只是一个名字。profile 后面那个数字是**交叉兼容性**，即基础层还能被读作哪种动态范围（8.4 是 HLG 兼容，8.1 是 HDR10 兼容）——它不是 level，level 数的是分辨率与码率档次。
- **`UnmetCapability` 不是 `PlaybackError`**。后者的每个 case 都是终止性的，于是"画面播了但第二视图缺失"或"音频编码被拒因而静音播放"无处可记，只能以一张没有解释的画面到达佩戴者。决定这类事实显示在哪里的唯一区别是**究竟播了没有**，所以那是这里唯一的轴；再细的分级（比如严重度阶梯）是各表面用不上的分类。这里的每个字段都已由 PlaybackCore 发布，本文件不探测设备：看不见的能力是事实集的缺口，不是可以用启发式推断的东西。
- **播放边界只接受已注册的字节来源**。远程调用方必须先注册字节来源，任意网络 URL 因此无法绕过 MediaSource 直接进入播放。
- **来源发现不越过持久化的用户覆盖**。文件自报的事实记录下来，但优先级低于交给这次技术会话的用户覆盖。
- **两个 RealityView host 都必须如实回答自己是否还在托管**。沉浸空间把一个标记 entity 放进自己的 content，用它的 `isActive` 回答 reconciler 的 `hostIsActive`；播放窗口曾经直接写 `true`。窗口被拆除之后，排队中的表面更新照样通过 host 检查、取走共享 entity 并认领 renderer，共享 entity 随即以 `presentation=window` 重铸，沉浸空间接过去的是为窗口铸的那一个，settlement 从此停在 `pixels=false`，四十余秒后入口以 `spatialPlaybackSurfaceUnavailable` 失败——佩戴者看到的是空间里一片全黑、音频照常、点击召不出控件，因为转场一直没有结束。窗口补上同一个标记后，`spatialVideoTopology skipped reason=inactiveHost scope=mainWindow` 出现在 `windowResidency residency=closed` 之后三个探针序号处，正好挡在原先那次认领的位置。结构规则见 `Scripts/rules/verify_playback_surface_structure.py`。
- **只有产品状态能证明一个 RealityView 永不落定**，经过的墙钟时间不能。首帧慢的表面在活动媒体请求的整个生命周期内保持 attach 资格。
- **`PlaybackUserVisibleIssue` 只接受有界的产品事实**，`Error` 与任意诊断字符串进不了这个类型，因此呈现代码永远不需要判断一段文本是否可以示人。
- **ProRes 解码器可用性经 `VTDecompressionSessionCreate` 实测**，不从渲染器的错误文本推断。见 `Tests/EnchronApp/VideoDecoderAvailabilityTests.swift`（真机 lane 专有，模拟器上按构造失败）。
- **旧构建暴露过一个 Apple 元数据专属的投影选项**，它已不再是用户可选的投影；解码时把它读成普通矩形视频，是为了保住那些偏好里带着旧值的媒体仍能播放。环境身份不再做偏好迁移：默认环境固定为 Quiet Room，不可配置，也没有黑夜模式（断言见 `EnvironmentSceneMappingTests`）。
- **`ViewingStatePolicy.mutation` 删除时长低于 `minimumContentDurationSeconds = 15 * 60` 的条目的观看状态**（`Modules/Playback/Domain/ViewingState.swift:50-56`）。只有长过这个常数的条目，退出后才留下可续播的状态。
- **local-aggregate 固件集里最长的一条是 120.064 s，整集都落在该常数之下**。`generated-viewing-storage-h264-16m01s-v1` 以 898 KB 承载 961.0 s，是集合里唯一在常数之上的条目，automatic-play-next-resume-policy 依赖它。见 `Scripts/verification/regression_preparation_adapter.py`。

## 面板的交叉淡变展开

面板的每一次切换（信息、设置、时间轴，以及它们的收起）是一次叠加动作：离开的内容在 `panelContentExit`（0.12 s）内淡出，进入的内容同时以 `panelContentEntrance` 淡入，而且从第一帧起就按自己的最终尺寸排版；外壳以 `panelSpring` 从旧尺寸行进到新尺寸，超出外壳的部分被 `clipShape` 裁掉、随外壳放大逐渐露出（Apple TV 的展开方式）。实现是 `FusedPlayerPanel.body` 里按 `expansion.layout` 取 `.id` 的内容层带不对称 opacity transition。glass 的 bounds 与形状都不能做动画：让外壳 frame 动画，系统在中途按矩形 bounds 画 glass、圆角只在起点终点出现；把可动画的 Shape 交给 `glassBackgroundEffect(in:)`，形状不逐帧更新，直接跳到终点（2026-09-07 模拟器与真机）。合成器逐帧处理的只有变换，所以切换时外壳先无动画钉在两个尺寸中较大的那个，整块 glass 视图按揭示尺寸与外壳尺寸之比做 `scaleEffect`，内容在 glass 内部反向缩放抵消，圆角随变换成椭圆但从不消失。内容必须留在 glass 视图内部：把 glass 做成兄弟层的板子会让内部的材质失去 glass 的 vibrancy 而发淡。揭示尺寸的起点在切换前无动画地钉为当前尺寸，落定用 `.removed` 完成条件，弹簧落稳后再清状态。原先的三步序列（内容退场→空外壳行进→内容入场）让新内容要等缩放结束才出现，2026-09-07 被否决。

控件整体隐藏（点画面）时面板保持当时的形态一起淡出，不在 `controlsVisible` 变 false 时重置 `expansion`——重置会让时间轴瞬间消失、普通控件先出现再淡出。重置发生在控件再次可见的那一刻（`disablesAnimations` 事务内）；窗口 ornament 与沉浸空间的 dock attachment 现在都是 opacity 归零、状态常驻，这一步对两者都是必需的。

窗口 ornament 在整个播放请求期间常驻 `.visible`，deck 内容不卸载，控件的显示与隐藏只是 deck 以 `controlsTransition` 改 opacity（Apple TV 的做法）；window bar 与 resize 手柄跟随控件可见性（`PlayerWindowSystemOverlayPolicy`：播放中控件隐藏时 `persistentSystemOverlays(.hidden)`，控件显示时 `.automatic`），佩戴者只能在控件可见时移动或缩放窗口，与 Apple TV 一致。此前的做法——出现时无动画装入、下一轮淡入，消失时淡完再卸载并把 ornament 置 `.hidden`——是为了绕开 ornament 尺寸变化被系统动画成从角落滑入；常驻后 ornament 的可见性在播放中不再翻转，尺寸变化只发生在面板展开，由面板自己的变换承担。控件隐藏时 ornament 仍占位，但 window bar 此时也隐藏，占位把 bar 顶远的问题（2026-09-07 真机）不再出现。

时间轴形态在窗口与沉浸空间统一为两行：第一行返回按钮、逐帧播放控制、缩放滑块（`PrecisionTimelineZoomSlider`，thickMaterial 胶囊），第二行只有胶片视口（`PrecisionTimelineView`，ultraThickMaterial），播放头时码作为胶囊贴在视口顶部中央；不再有整块列表材质、信息栏与 dock 的设置按钮。dock 的设置形态是第一行返回与恢复默认两个圆形按钮、其下三个放置滑块坐在一块 thickMaterial 上；信息栏展开后是左上返回按钮、标题、详情正文（无详情留空）与技术信息行，没有图片与其他按钮。这个次序没有测试覆盖：`Tests/PlaybackPresentationTests/PlaybackPanelExpansionTests.swift` 的 5 个测试只验证 `PlaybackPanelExpansion` 这个 enum 的块切换，不涉及按钮、滑块或内容的排列次序。

## 观影环境场景

- **Reality Composer Pro 3.0（1A196）的 `.reality` 导出会丢掉 `active: false` 的实体**：quiet_room 里禁用的 `Sky` 与 `floor2` 在导出物里不存在，运行时不需要再按名禁用（2026-09-11 用 macOS RealityKit 加载导出物核对）。带 `DockingRegionComponent` 的实体必须是启用状态导出，否则场景包求不出静止位姿、`load()` 抛出 `entityMissing("DockingRegion")`。2026-09-11 ocean 的 `ScreenPreview` 在 RCP 里被设为未激活，导出物里整个消失，当时的场景包仍按 `ScreenPreview` 求位姿，海洋场景因此加载失败。
- **同一版本的 RCP 在无头模式下加载 `OceanProbePlugin.dylib` 即退出**，没有日志、没有崩溃报告，`--load-project` 之后再无输出；不加载插件时 ocean 正常导出，但 `OceanProbeComponent` 被丢弃并打出 `No component registered`。Ocean 场景包因此在 `load()` 里按 `world.tm_entity` 的作者值重新挂上该组件；作者值变化时要同步 `OceanEnvironmentScene.authoredSimulation`。
- **RCP 3.0 无头模式带 `--always-load-plugins` 时会重签名并以新的 loader 副本重启自己**（`~/Library/Application Support/com.apple.realitycomposerpro/loaders/<uuid>/`），父进程退出、导出脚本拿不到产物，重启出来的进程还会留在后台；quiet_room 没有任何插件也如此（2026-09-11）。两个场景都用 `--without-plugins` 导出。
- **Quiet Room 的瓦片在加载时合并成 GPU 实例**：作者把 1920 块 `Floor_*`/`Ceil_*` 瓦片当作独立实体摆放，RealityKit 对每个实体各出一个 draw call，位姿变化时场景包也要逐实体改写材质。`QuietRoomEnvironmentScene.load()` 按名字前缀（Floor/Ceil）与变体后缀（A/B/C）分组，每组一个宿主实体带原 `ModelComponent` 与 `MeshInstancesComponent`（visionOS 26 起），实例变换取瓦片网格实体相对场景根的矩阵，原实体移除；`FloorScreenGlow` 的更新因此只触及六个宿主。`screen_forward` 由屏幕状态的法向写入，`FloorScreenGlow_fragment` 用它把屏幕平面之后的表面从屏幕光里去掉。

- **Ocean 水面的屏幕倒影用 Apple 的 `Reflection Specular`，只叠加、不替换天空反射**（2026-09-12 头显验证后定稿）：节点的反射起点接水面世界坐标，法线接 `mix((0,1,0), 波浪法线, ReflectionRoughness)`，`antialiasingStrength` 接 `ReflectionEdgeFeather`；单条镜面反射线只有打中与没打中两种结果，倒影里会出现边缘锐利的空洞，所以法线再沿 ±X、±Z 偏开 `ReflectionEdgeFeather`（默认 0.08）各取一次，4 次结果按各自覆盖度加权平均，部分打中的像素成为渐变；输出颜色不再调色（旧的 0.5 为轴的对比度会把线性亮度低于约 0.054 的倒影压成负值），乘节点的 alpha、Fresnel 与 `ReflectionStrength` 后加到发光项。曾让 PBR `specular` 按倒影覆盖度从 0.25 降到 0，想以屏幕倒影替换天空反射，结果朝向观众的波面 Fresnel 只有约 0.02、屏幕项几乎为零，覆盖处只剩深色水体，出现黑块黑边，已恢复为常数 0.25。旧反射子图里按屏幕位于 x = ScreenCenterX 平面写的“扭曲过渡”（`(ScreenCenterX − x) ÷ 视线.x`）在屏幕正对前方时于 x = 0 过零换号，接进 Apple 节点后倒影正中出现一条竖直接缝；Apple 节点因此不再使用那套轴向计算的任何中间量。
- **Ocean 运行时环境光的地平线以下是“反射天空的远海”，不是一块深色**（2026-09-12）：水面 PBR `specular` 0.25 会沿反射方向清晰地映出 `RuntimeEnvironmentLighting` 生成的经纬图。原来地平线以下是常数深海色 (0.055, 0.070, 0.086)，只有地平线天空的 1/5–1/4，且只有约 4° 的 smoothstep 过渡；朝观众倾斜的浪面把反射压到地平线以下时，映出边缘清晰、随浪移动的深色块，远看混成真实的海面纹理，近看和斜看就是纯色块，与屏幕倒影叠在一起尤其刺眼。现在 `SkyAppearance.color(towards:)` 对俯角 δ 的方向返回 `F·天空(δ) + (1 − F)·seaColor`，F = 0.02 + 0.98·(1 − sin δ)⁵（远处平海以 cos θ = sin δ 入射反射天空），在地平线处连续等于天空，俯角 10° 约 40% 天空、30° 约 5%。同时 OceanVideo 的 `WaterRoughness` 0.10 → 0.18、`NormalStrength` 1.3 → 1.0。RCP 用自带的环境光，看不到这项修改的效果，只能在设备上判断。
- **Ocean 水面有一项“屏幕照亮的水体”透光，按前向散射计算**（2026-09-12）：真实海面上光源方向那片水更亮、偏青绿，是光射入浪面、在水中被逐通道吸收后从朝向观众的一侧散射出来（红光约 0.35/m、绿光约 0.06/m、带浮游生物时蓝光约 0.08/m，3 m 路程透过率约 (0.35, 0.81, 0.79)），且水中散射强烈偏向原前进方向，只在观众、浪与光源大致成一线处明显；周围的深蓝则只是水面反射的夜空。OceanVideo_fragment 在发光项上加 `屏幕漫射光 × ScreenGlowTint × clamp(dot(normalize(P − Q), 视线), 0, 1)^ScreenGlowPower × 1/(1 + (|P − Q|/(2·屏幕半宽))²) × 列遮罩 × (1 − F) × (1 − 泡沫) × ScreenGlowStrength`。u 是视线经 P 延伸到屏幕平面时相对屏幕中心的横向位置（米），Q 是屏幕上横向坐标为 clamp(u, −半宽, 半宽) 的点；横向轴取屏幕水平右向量 (ScreenRightX, 0, ScreenRightZ)，朝向轴取 (−ScreenRightZ, 0, ScreenRightX)，设备上由场景包每帧按真实屏幕写入，RCP 里取 `Video` 停靠实体的朝向（当前朝 +Z，右向量 (1, 0, 0)）。两者不一致时横向与朝向互换，透光塌成沿屏幕中线伸向观众的一条细线（2026-09-12 在 world 根节点仍偏航 −90°、`Video` 朝 world −x 时出现过）；旋转 `Video` 后要同步这两个值。列遮罩为 `1 − smoothstep(1 − ScreenGlowFeather, 1 + ScreenGlowFeather, |u|/半宽)`，漫射光的采样横坐标也取 u/半宽。浪能把透射光在竖直方向大角度折弯，横向偏折只来自横向坡度，与倒影的横向展宽同源，所以透光与倒影共用同一列，屏幕越远两者在画面上同样变窄。以屏幕中心单点算横向角度时，透光在观众端的视宽等于散射瓣张角（ScreenGlowPower 9.5 时约 ±22°），不随屏幕距离缩小，远看呈从屏幕根部张开的扇形（2026-09-12 修正：35 m 处旧版半亮半宽从观众端 13.9° 收到屏幕端 2.8°，新版三处在 10.5°–11.5°，倒影 11.5°）。屏幕漫射光取 Apple `Reflection Diffuse`（衰减贴图接 `pure_white`，衰减由上式负责），颜色随视频逐帧变化：红色画面几乎不透光，只剩水面上的红色倒影。`ScreenGlowTint` 在 RCP 里以 ACES2065-1 存储，默认值是线性 Rec.709 (0.35, 0.81, 0.79) 换算后的 (0.604, 0.767, 0.784)。
- **RCP 视口里的海面来自另一份 OceanProbe**：Reality Composer Pro 按 `__project_settings` 加载 `Xrplay_scene/scratch/OceanProbePlugin/.build/out/Products/Release/libOceanProbePlugin.dylib`，由该插件自己的 `Sources/OceanProbePlugin` 编译，与 Enchron 的 `Packages/OceanEnvironment/Sources/OceanEnvironment/Vendor/OceanProbe` 是两份各自维护的源码。只改其中一份时，RCP 预览与设备表现会不一致（2026-09-12 环境光修复先只进了 Enchron，RCP 里深色块依旧）。改 OceanProbe 时两份都要改，插件用 `Xrplay_scene/scratch/OceanProbePlugin/Scripts/verify_ocean_probe.py` 的 `build_and_deploy_plugin()` 重新编译部署，然后重启 RCP。RCP 预览里 `ScreenCenterX/Y/Z`、`ScreenHalfWidth/Height` 用的是材质里的作者值，设备上由场景包每次 `update` 写入真实屏幕位姿，作者值应与停靠实体一致，否则依赖屏幕位置的项（如屏幕透光）在 RCP 里会失效。
- **Ocean 的海面不在 `.reality` 里**：`OceanProbeSystem` 在运行时从 `OceanMaterialSource` 复制材质、生成 `OceanProbeSurface` 网格并跑 512² 四级联 FFT；这个 System 与组件必须在加载前注册（`OceanEnvironmentScene.registerRuntimeIfNeeded()`）。视频反射参数写在 `OceanMaterialSource` 的材质上，System 每帧把变化同步到生成的表面。
- **Quiet Room 地面与天花板的屏幕光在房间边界强制归零**（2026-09-12）：地砖用 unlit 材质，颜色 = (地砖 × floor_gain + screen_lift) × 屏幕光，场景里没有其他光源。换用 Apple `Reflection Diffuse` 后输出只取 `clamp(Apple 漫射光 × screen_light_gain × 法线项, screen_glow_clamp_max)`，原有的 `screen_range`、`screen_attenuation_*`、`screen_edge_feather` 衰减节点仍在图里但不接输出。Apple 默认衰减贴图（`video_dock_attenuation.exr`，外缘为 0）按材质里的映射，在房间侧边 x = ±16 m 处最高仍有中心峰值的 0.17%；增益 10、中心被 0.8 截平时，侧边约为线性 1% 量级，显示编码后约 10% 灰，在纯黑背景前形成可见边界，要到 ±24 m 才降到 0.01%。`FloorScreenGlow_fragment` 因此在屏幕背面遮罩上再乘房间遮罩 `smoothstep(0, room_edge_fade, room_half_width − |偏移·右向量|) × smoothstep(0, room_edge_fade, room_depth − 偏移·screen_forward)`，偏移相对 `screen_center`，右向量为 `normalize(cross(上, screen_forward))`。Quiet Room 按“移动观众”整体平移，运行时写入的 `screen_center`、`screen_forward` 随之变化，遮罩以屏幕为参照而不用世界坐标。默认 room_half_width 16 m、room_depth 25.78 m（地砖后沿 z 17.8 m 减屏幕 z −7.98 m）、room_edge_fade 3 m；前沿止于屏幕平面，由原有的屏幕背面遮罩（screen_back_softness 0.5 m）归零。改动地砖范围后要同步 room_half_width 与 room_depth。
- **Ocean 场景的坐标轴与 visionOS 一致**（2026-09-12）：`world` 根节点只有 (0, −5, 0) 的位移、旋转为零，观众在原点朝 −Z；`Video` 停靠实体局部 (0, 4, −15)、旋转为零，世界中心 (0, −1, −15)、朝 +Z。OceanProbe 的风向与涌浪方向在 FFT 网格的 (x, z) 平面上从 +X 转向 +Z 计角，传播方向为 (cos θ, 0, sin θ)：涌浪 165°（与 Z 轴成 75°，横过视线），风 220°，交叉浪角是相对风向的偏移。根节点此前偏航 −90°，RCP 里的屏幕朝 world −x，RCP 预览与设备视角相差 90°，海浪、天空与光照方位在两边对不上；归零时只移动了 `Video` 与未激活的 `ScreenPreview`，风向与涌浪方向各加 90°，天空、`OceanSoftLight` 与 `SunDirection` 不动（`SunDirection` 本就与归零后的光照一致）。场景包的 `authoredSimulation` 覆盖 RCP 里的组件值，两处必须同步。
- **OceanVideo 的 `VideoTexture` 在运行时写不进去**（2026-09-12）：`ShaderGraphMaterial.setParameter` 对它的任何值都抛 `incorrectTypeForParameterName`，包括从同一材质读回的原值和新生成的 2D `TextureResource`。旧的同步在任一参数变化时重写全部参数，这一项失败使整次同步作废：RCP 预览里所有参数调节都不生效（一次会话记录 23 889 条 `OceanWater parameter synchronization failed`），设备上场景包写入的屏幕位姿与强度也停留在渲染器创建时的作者值。同步现只写变化的参数，被拒收的参数记为 `OceanWater surface rejected parameters`，不影响其余参数。场景包每帧对 `VideoTexture` 的 `try?` 写入同样静默失败，设备上它始终是作者值 `pure_white`。

- **屏幕的静止位姿由场景内带 `DockingRegionComponent` 的实体给出**：停靠区域朝向局部 +Z。读的是世界变换（Ocean 的场景根带 −90° 偏航与 (0,−5,0) 位移，局部值没有意义），法向取局部 +Z，竖直轴由世界 Y 对法向做投影得到，法向背对原点时连同右向一起翻转；半宽取组件宽度的一半乘局部 X 轴的缩放，半高取描述符默认屏幕高度的一半。Apple 把停靠区域固定为 2.4:1，由宽度推高度会得到 5.93 m 而不是 16:9 屏幕的 8 m，Quiet Room 的屏幕下沿会因此抬高约 1 m。派生量是底边高度 `中心.y − 半高`、距离 `|(中心.x, 中心.z)|`、偏航 `atan2(−中心.x, −中心.z)` 与屏幕高度 `2 × 半高`。同一个实体也是系统视频反射的发射区域，场景包每次 `update` 用 `alignDockingRegion(to:)` 把它移到屏幕的实际中心与朝向、宽度设为屏幕宽度。描述符里的默认距离与默认高度是同一组作者值的静态副本；加载时两者相差超过 1 cm 记一条 `restPoseDrift` 探针，仍按面片的值走。场景不再需要空的 `PlaybackSurfaceAnchor` 实体，`ImmersiveSpaceView` 自己在静止中心建一个名为 `EnchronPlaybackSurfaceAnchor` 的空实体挂载视频。
- **屏幕以底边为锚绕佩戴者抬升，高度优先**：枢轴 P = (0, 底边高度, 0)，底边中点 B = P + 距离 × (0, sin e, −cos e)，上向量 (0, cos e, sin e)，法向 (0, −sin e, cos e)，右向 (1, 0, 0)，中心 = B + 半高 × 上向量，整组再绕 Y 轴转偏航角。改屏幕高度只向上长，底边不动。有天花板的场景在顶边 `B + 2 × 半高 × 上向量` 越过 `天花板 − 余量` 时沿视线缩短距离，90° 时平放的屏幕贴在天花板下方。Quiet Room 的距离调节同时移动场景根节点与屏幕：根节点沿偏航方向平移 `静止距离 − 请求距离`，屏幕按请求距离放置，平移后的墙面恰好落在同一距离，所以屏幕始终贴在作者摆放的墙面上，屏幕与房间一起远离或靠近；Ocean 与占位只移动屏幕。所有环境的屏幕高度固定为 8 m（各场景 `screenHeightRangeMeters` 为 8…8），面板不再提供屏幕尺寸滑条，宽度随视频宽高比。面板的 Height 是观看高度：取值 h（−2…2 m，步长 0.1）时，场景根节点与屏幕一起沿世界 Y 平移 −h，距离与高度分别把世界的 Z 与 Y 交给用户；天花板钳制在平移之前按房间坐标计算，所以不受高度影响。
- **反射纹理来自 `AVSampleBufferVideoRenderer.displayedPixelBuffer()`，由 `VTPixelTransferSession` 解码缩放**：visionOS 上这个像素缓冲是 Apple 的无损压缩 10-bit 打包双平面格式 `'&xv0'`（`kCVPixelFormatType_Lossless_420YpCbCr10PackedBiPlanarVideoRange`，数值 645428784），不能当作普通的 8-bit／16-bit 平面经 `CVMetalTextureCache` 读取；按普通平面读出来的是固定的饱和青蓝色（帧平均约 R 0.03、G 3.8、B 3.9），与画面无关。`VTPixelTransferSession` 负责解压、缩到 128×72，并转成 Rec.709 原色、线性传递函数的 `64RGBAHalf`；缩放本身做面积平均，逐帧采样不会出现单像素采样的闪烁。每个 RealityKit 场景更新都查询一次当前显示的像素缓冲，缓冲对象变化时才重做，也就是逐视频帧采样、不做时间平滑；compute kernel 只把线性值夹在 0…16 并生成 8 级 mipmap。早期版本每秒采样 15 次并做 0.22 秒时间常数的指数混合，剪辑切换后地面光要约 0.7 秒才追上画面，在头显里造成明显的滞后感和眩晕。纹理对象只创建一次，场景包在第一次拿到纹理时收到一次 `update`。Quiet Room 材质的 `screen_lod_near`/`screen_lod_far` 是在 RCP 里对全尺寸测试图调出来的，场景包按 log2(1920 ÷ 纹理宽) 把它们减小，128 宽时约 3.9 级。每 30 次重做把最小一级 mipmap（整帧平均色）读回 CPU，记一条 `reflectionFrameAverage` evidence 探针，用来确认纹理随画面变化。这条链路只在设备上有像素时才走通，因此四个节点各记一条 evidence 探针：管线建成（`reflectionPipelinePrepared`，尺寸与像素格式）、首帧编码成功（`reflectionFrameEncoded`，像素格式、平面数、帧序号）、首次把非空纹理交给场景（`reflectionTextureDelivered`）与失败（`reflectionFailure`，错误文本；`failure` 一旦非空就不再尝试）。
- **反射纹理天然比屏幕晚几帧，系统播放器没有取未来帧的接口**：`AVSampleBufferVideoRenderer` 的像素输出只有 `copyDisplayedPixelBuffer`／`displayedPixelBuffer()`，头文件原文是 "the pixel buffer currently displayed"（visionOS 27 SDK `AVSampleBufferVideoRenderer.h`）；Enchron 交给它的是压缩样本，解码在渲染器内部，App 在显示之前拿不到解码帧。取到的帧再经 GPU 缩放和 RealityKit 渲染进程上屏，地面光落后屏幕约数个渲染帧，头显里剪辑切换时肉眼可见。按预测时间取未来帧的 `AVPlayerItemVideoOutput.copyPixelBuffer(forItemTime:)` 只属于 `AVPlayer`。系统自带的视频反射（Shader Graph 的 `Reflection Specular`／`Reflection Diffuse` 节点）由系统同步计算，但文档只把它描述为 `AVPlayerViewController` 停靠进 `DockingRegionComponent` 时的行为（https://developer.apple.com/documentation/visionos/enabling-video-reflections-in-an-immersive-environment ，WWDC24 10115），`VideoPlayerComponent` 在 SDK 27 里没有任何反射相关属性，它能否驱动这两个节点没有文档，需要设备实验。不重复解码而又逐帧对齐的另一条路是 App 自己解码、把解码后的 `CVPixelBuffer` 交给渲染器（`recommendedPixelBufferAttributes`，visionOS 26+），这会把解码帧的内存、HDR 与 Dolby Vision 处理移进播放引擎。

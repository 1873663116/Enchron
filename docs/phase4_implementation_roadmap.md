# Phase 4 产出：施工路线图与里程碑

> 本文档将 Phase 1-3 的架构设计转化为具体的开发计划。遵循"先跑通再做全"原则：用首个垂直切片验证技术栈，再逐步扩展功能。

---

## 首个垂直切片：v0.1 — "本地视频窗口播放"

### 为什么选这个？

这个切片**贯穿三个核心模块**（FileBrowsing → PlaybackCore → PlayerUI），同时验证了**最大的技术风险**（libmpv 在 visionOS 上能否正常工作）。如果这条路走不通，越早知道越好。

### v0.1 要做什么？

```
用户打开 App → 看到文件浏览界面 → 选择本地视频文件 → 视频在窗口中播放
```

涉及的模块和文件（最小集合）：

| 模块 | 要做的事 | 关键验证点 |
|---|---|---|
| **App/** | 应用入口 + MainView 外壳 | visionOS WindowGroup 能正常启动 |
| **FileBrowsing** | 只做本地文件浏览（不做 SMB/WebDAV） | 能列出本地视频文件并返回 URL |
| **PlaybackCore** | libmpv 初始化 + 硬件解码 + 基础事件循环 | ⚠️ **libmpv 能在 visionOS 上编译和运行** |
| **PlayerUI** | 窗口模式播放（MTKView） + 最基础的播放/暂停 | CVPixelBuffer → MTLTexture → MTKView 显示正常 |
| **Persistence** | 不做（v0.1 不需要） | — |
| **SpatialScene** | 不做（v0.1 不进入沉浸空间） | — |
| **Settings** | 不做 | — |

### v0.1 验收标准

- [ ] App 在 visionOS 真机上正常启动（模拟器仅用于 UI 辅助验证）
- [ ] 能浏览本地文件夹中的视频文件
- [ ] 选择一个 MP4/MKV 文件后，视频在窗口中播放
- [ ] 有画面、有声音
- [ ] 能暂停和恢复播放
- [ ] 连续播放 30 分钟无崩溃、无明显内存持续增长

### v0.1 测试用例（最小集，建议现在就设计）

| 用例ID | 场景 | 预期结果 |
|---|---|---|
| TC-V01 | 冷启动进入主界面 | 3 秒内看到文件浏览入口，无崩溃 |
| TC-V02 | 打开本地 MP4 文件 | 5 秒内出画出声，播放状态为 Playing |
| TC-V03 | 播放中点击暂停/恢复 | 状态准确切换，音画同步恢复 |
| TC-V04 | 连续播放 30 分钟 | 无崩溃、无明显内存持续增长 |
| TC-V05 | 打开不支持格式文件 | 文件不可选或给出明确错误提示，不崩溃 |

## 技术风险与应对

| 风险 | 可能性 | 影响 | 应对方案 |
|---|---|---|---|
| libmpv 无法在 visionOS 上编译 | 中 | 致命 | v0.1 首先验证；备选方案：FFmpeg 直接集成 |
| mpv_render 软件渲染性能不足 | 低 | 高 | 测试 4K/8K 帧率；可尝试 GPU 回调渲染 |
| CVPixelBuffer → TextureResource 链路 HDR 色彩丢失 | 中 | 中 | v0.2 验证 HDR 管线；检查像素格式和色彩空间标签 |
| RealityKit 球体内壁投影画面畸变 | 低 | 中 | 使用正确的 UV 映射；参考等距柱状投影算法 |
| Wi-Fi 带宽不足导致 8K 远程播放卡顿 | 高 | 低 | 这是用户侧网络问题，非软件问题；提供缓冲状态提示 |
| libmpv 事件积压导致状态错乱 | 中 | 高 | 建立独立事件循环 + 背压策略（高频事件合并、队列监控告警） |
| 长时间播放温升导致降频/续航下降 | 中 | 中 | 增加真机长时门禁与功耗预算，按模式做差异化渲染优化 |

## 执行节奏说明

本方案不再绑定固定“人工工期”估算，改为**里程碑验收门禁驱动**：

1. 每个版本以“验收标准全部通过”作为进入下一里程碑的唯一条件。
2. Agent 可并行推进多个子任务，但不得跳过前置门禁（如 libmpv 可用性、真机稳定性、异常恢复）。
3. 若某里程碑出现阻断性风险（例如核心解码链路不可用），立即回退到风险应对分支，不继续堆叠后续功能。
4. 每个里程碑开工前先补齐该里程碑最小测试用例（冒烟 + 核心链路 + 异常路径），再并行开发。

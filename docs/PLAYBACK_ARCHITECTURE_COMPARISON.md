# 播放架构对比：原始需求、两代实现、是否撤销

本文回答三个问题：最初要解决什么、两代架构各自怎么做、要不要撤销。每一条结论都标出证据来源；没有实测的条目直接写明未测。

## 一、最初的需求

一，ISO 打开过慢。
二，ISO 里的音轨要有正确的显示名称。
三，ISO 里的字幕轨要有正确的显示名称，并且能正常显示。

这三条之外的内容，包括共享解复用源、三条车道、按呈现时间戳交付、车道接入契约，都是后续为解决前一条需求或修复由此引入的问题而增加的。

## 二、两代实现的机制

上一代：每条车道自己打开输入。视频、音频、字幕各自对同一个远端 ISO 建立连接、解析蓝光目录、读 playlist、解复用。切换音轨与跳转都重建对应的输入。

这一代：一个解复用源打开容器一次，持有读取位置与保留历史。视频、音频、字幕三条车道从同一个源取出各自的流。跳转移动容器的读取位置，不重新打开容器。切换音轨时接管该音频流，不重新打开容器。

## 三、证据

一，容器只描述一次。九十分钟内日志出现 `source.description` 两次，而车道挂载日志 `attach.open` 与 `subtitle.lane.attached` 共十七次。若每次挂载都重新打开容器，这两个数字应当同量级。

二，挂载不移动容器。跳转与切换之后出现的是 `video.reader.bind`、`audio.attach.open reason=seek`、`subtitle.lane.attached`，不出现新的 `source.description`。

三，这一代引入了新的失败模式。切换音轨后新车道从队列最老的包开始，落后播放位置十四秒：

```
21:53:57.775  audio.attach.open reason=selection index=1 codec=truehd
              queuedBefore=43098 queuedAfter=74324 headBefore=1300.815
```

当时播放位置约 1315 秒。

四，形式化检查确认这类缺陷在没有接入契约时必然存在：接管不清除播放位置之前的包，就存在一条合法执行路径让车道播过期数据。检查在 `Scripts/playback/formal/run.sh`。

## 四、视频是否需要新规则

不需要。视频车道创建时就带起始位置，等价于「从播放位置开始」。新的接入契约对视频是既有行为，对音频与字幕是缺失的行为。

## 五、是否在回到旧架构

不是。区别只有一个数字：容器打开的次数量级。

```
旧：每次打开、跳转、切换  ──▶  一次容器打开 + 一次 playlist 解析 + 一次探测
新：每次打开               ──▶  一次容器打开
    每次跳转、切换         ──▶  不打开容器，只移动读取位置或接管流
```

跳转与切换时「重建读取器」在两代里都发生。差别在于重建时是否需要重新打开容器并重新探测。

## 六、撤销的收益与代价

撤销到这一代之前，恢复的行为是：切换与跳转重新打开容器、重新解析 playlist、重新探测轨道。打开慢的原始问题随之回来，因为打开慢的原因正是重复的容器打开与探测。

保留这一代，保留的问题是：音频与字幕车道的接入契约缺失。该契约的修复范围是源的一个裁剪入口与一个期限判定，不涉及容器打开路径。

## 七、未测

一，ISO 从打开到起播的耗时，两代之间没有做前后对比测量。这是唯一能定论「快了多少」的数字，测法：在同一模拟器上分别构建两个提交，用同一部 ISO 记录从发出播放请求到 `readiness.state state=playable` 的时间。

二，切换音轨与跳转的耗时，两代之间没有对比测量。

## 八、建议

一，不整体撤销。容器只打开一次是原始需求「打开慢」的直接解，撤销它等于撤销这条需求的解。

二，冻结架构。除音频与字幕的接入契约外，不再改动解复用源与车道结构。

三，接入契约的修复分两步，各自可独立验收：源在交出流之前丢弃播放位置之前的包；会话对已选车道设期限，超期进入加载态。

四，若需要「快了多少」这个数字，先做第七节第一条的前后测量，再决定是否继续保留这一代。

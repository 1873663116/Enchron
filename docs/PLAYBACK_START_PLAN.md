# 播放起播的执行与验收方案

本文规定「远程源起播不可用」这一组缺陷的修复顺序与验收方式。它描述要达成的目标状态、先测什么、分几步改、每一步用什么证据判定通过。现状与证据缺口分别列在各阶段内。

## 一、要解决的缺陷

起播路径上有四个互相关联的缺陷。

音频就绪由墙钟计时判定。等待超过五秒即判音频失败，失败后音频轨道被永久撤除，视频继续。这条判定无法区分「数据还没到」与「数据不会来」。

失败的责任落在单个消费者身上。音频可以单独消失，会话因此能停留在「视频在播、音频已被移除」这种状态。

共享数据源没有唯一所有者。视频、音频、字幕、探测、seek 都按 URL 字符串挂到同一个解复用会话上，谁先挂源就以谁的名义创建，读者拿不到纪元，源被重建后旧读者无法被发现。

「文件里有什么」被派生多次。浏览阶段一份元数据、会话打开一份流表、音频与字幕各自持有加载器兜底，几份之间靠手工合并对齐。任何一处改动都要同步多处，这是改一处坏另一处的结构原因。

## 二、目标状态

一个会话、一份描述、一个状态机、一个失败判定。

```
SourceSession（唯一 AVFormatContext，纪元 E）
  ├─ SourceDescription（不可变，绑定 E）
  │    容器事实、流表（含按 PID 合并的语言）、缺省选择
  └─ Readiness（会话级状态机）
        loading / playable / stalled / failed

video attachment   audio attachment   subtitle attachment
  按 (E, streamIndex) 绑定，只取包，不探测、不单独失败
```

四条不变量。

一，可播性是联合判据。required 中的每条流都攒到播放头加预滚时长，会话才进入 playable。required 由描述决定：存在视频则含视频，存在音频则含音频；无音轨文件退化为仅视频。

二，数据状态与传输意图分离。数据未就绪时界面显示加载中，不显示暂停。暂停只表达用户意图。

三，失败属于会话。消费者不单独失败，只处于等待。文件没有音轨是描述里的能力事实，不是失败。

四，判据用呈现时间，不用字节常数。就绪看每条流攒到的呈现时间；缺陷看一条流的呈现时间是否在另一条推进时停住。任何阈值来自播放语义，不来自某一个文件的实测。

## 三、阶段零：先测量，不改行为

目标：拿到判定基线与验收起点。全部为只读诊断，不改变任何播放行为。

第一条，首个可用单元的时间与字节。对同一次冷启动打开，记录视频首个可解码帧、音频首个可解码单元各自的到达时刻、呈现时间戳与源侧字节偏移。输出一行：`start.firstUnit lane=video|audio atMs= pts= bytes=`。

第二条，时间戳同基验证。记录视频与音频首包的时间戳基准，确认两条流可比较。若不同基，先修基准再谈判据。

第三条，队列深度与订阅状态。音频读取器的每次阻塞超过两秒即记录 `audio.read.stall seconds= codec= channels= index= queued=`，其中 `queued` 为该流队列当前包数。

第四条，冷启动与预热对比。同一文件做两次打开：冷启动一次，随后 seek 一次。记录两次的首个音频包到达时刻。

判定与去向：

若冷启动首个音频包明显晚于视频首帧且 `queued` 长时间为零，先修纪元与队列归属，再进入阶段一。

若 `queued` 有包而音频不交付，问题在交付与渲染器，阶段二优先。

若两者都正常，则现有缺陷只在界面状态与失败模型，阶段三优先。

## 四、阶段一：一个源描述

范围：`Packages/PlaybackCore/Sources/PlaybackCore`。

一，`SourceDescription` 为不可变值类型，带纪元，包含容器事实、流表、缺省选择。语言在流表生成时按 PID 合并，此后不再有第二次填充。

二，会话创建描述，且只创建一次。音频与字幕的 `tracks(...)` 改为读描述，删除各自的兜底加载器；`SystemMediaSourceInformationLoader` 只保留会话内一个实例。

三，读者按 `(epoch, streamIndex)` 绑定。绑定失败立即报错，不允许在读取时无限阻塞。

四，浏览期元数据降级为预览：它不参与播放期描述，删除手工合并。

验收：一次播放中 `demux.open` 计数为一；描述生成后加载器调用计数为零；音频、字幕、界面三处的流表逐项相等。

## 五、阶段二：就绪状态机

一，删除 `waitForAudioPreroll` 的墙钟判失败逻辑。起播闸门等待事件：视频首帧可解码、required 中每条流攒够预滚呈现时间。

二，`stalled` 由源侧字节进展判定，是会话级可恢复状态。恢复后继续，不重建会话。

三，`retireAudio` 只允许由读取错误或渲染器失败调用，不允许由超时调用。

四，界面映射：数据未就绪显示加载中；`playable` 后按用户意图显示播放或暂停。

验收：人为把首次音频数据延迟到超过旧常数，会话保持加载中，不开始播放、不撤音频；数据到达后进入 playable 并出声。人为停住音频队列，判据报缺陷并保持加载中。

## 六、阶段三：失败与会话一致

一，失败只产生于源错误或解码恢复耗尽，携带单一原因，全部消费者一起转入。

二，删除「视频在播、音频缺失」这一可达状态。可用会话状态枚举穷举断言。

三，无音轨文件在描述中标记，界面显示无音轨，不进入失败。

验收：注入源错误，视频与音频同时进入失败，原因一致；无音轨文件正常播放且界面不报失败。

## 七、阶段四：切换路径统一

音频切换、字幕切换、seek 三条路径统一为「重新绑定 attachment」，不重建会话、不触碰描述。

验收：播放中切换字幕轨道，音频 attachment 的纪元与状态不变，音频持续出声；切换音频轨道后视频不中断；seek 后两条流都重新就绪。

## 八、验收矩阵

结构层。`demux.open` 一次；描述唯一；三处流表相等；无消费者侧加载器；无按文件实测的字节常数。

场景层。远程冷启动不 seek 出声；同一内容 seek 后出声；Emby 同一条目两种入场都出声；无音轨文件正常；字幕切换不打断音频。

否定层。音频延迟超过任意旧常数仍不出错；音频队列停住必须报缺陷；交织较差的文件不误报；「视频在播、音频缺失」不可达。

每一层的证据是日志行、断言或测试名，不是口头结论。

## 九、风险与回滚

阶段一改动面最大，涉及会话初始化和三个 provider 的构造，测试需要重写一批。回滚以阶段为单位：每阶段独立可回退，阶段零不改变行为可长期保留。

## 十、未决

一，流式来源在打开时没有容器索引，「每条流已攒到的呈现时间」在首包之前的初值需要定义。

二，时间戳同基尚未验证，阶段零第二条输出前不进入阶段二。

三，Emby 路径中音频包未到达的具体归属（纪元错配或队列未填充）未定位，阶段零第四条给出指向。

四，字幕帧的时间基与此处的音频视频时间基是否一致未验证。

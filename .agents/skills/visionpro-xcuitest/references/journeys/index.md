## 合同与执行语义

一次全绿授权的完整话术：「以下旅程全部通过；另有 N 个声明过而无人看守的证据点（附录 A）、M 个未完成的人工感知项（附录 B）、K 个内容条件缺口（附录 C）。」绿灯只对旅程负责，三个附录是绿灯明示不覆盖的范围，每轮报告必须原样携带。

执行语义：每条旅程从干净状态开始，旅程之间不传递状态，任何一条可单独重跑。旅程内某步失败即中止本旅程，其后步骤记为未评估而非缺陷；已通过步骤的证据保留。通道故障或内容条件不满足导致的中止记为「作废」，不计缺陷。可达性矩阵保留为第 0 层，仅三种情况运行：源码变动波及判定点锚点、旅程步骤以「够不着」签名失败、明确要求全量审计。

**一条旅程何时成立**：当且仅当它拥有一段别处不会走到的真实使用过程。**界面上存在一个页面，不构成立一条旅程的理由**——按页面分是特性分类，不是使用过程，而分类会把设备开销（清空、注入、播到稳态）重复付好几遍，去换几秒钟的断言。判断顺序是：这些断言发生在哪条已有旅程已经到达的状态里，就并进那一条；没有任何旅程会到达那个状态，才新立一条。

**操作能否触达属第 0 层，不属旅程**。旅程问的是操作**做了它宣称的事没有**，可达性矩阵问的是操作**够不够得着**。两者不重复。

## 判读模型

判读分三层，分界规则是「这个断言的真假由谁决定」：

**机械层（脚本断言）**：结构化字段的相等与阈值判断。lifecycle、position、session 身份、audioTrack、投影与立体字段、传递函数、服务器侧进度。真假由代码决定，出错即失败，无裁量。

**判断层（Agent 判读）**：不可写成机械规则的情境判断，依据两类采集：
- 内部采帧：间隔至少 1 秒截 3 帧。判读内容是否真实（非纯色、非黑屏、非冻结）、帧间是否连续（证明持续解码）、有无整体色偏（P5 紫绿类在截图上直接可见）、HDR 片有无未解释 PQ 的灰雾形态。
- 麦克风采集：麦克风置于扬声器旁，采集后经音频分析工具输出结构化结果（主导频率、静音段、粗同步），Agent 判读结论。生成向量的每条音轨带独特脉冲频率（如 880Hz 对轨 1、440Hz 对轨 2），轨道切换的可闻性因此可机判。
- **判读者自检**：每轮判读开始前，先判一组已知阴阳样本（furyroad-with-dv 与 stripped 对照）。判不出已知坏样本，本轮全部判断层结论作废。

**人工层（佩戴者）**：亮度是否足够、饱和度偏好、空间化跟手感、切换突兀感、舒适度、真实手势。配合模式沿用既定裁决：Agent 供片单与「每部看什么」，用户任意顺序手点，Agent 后台记录。

## 重复动作规则

十三条旅程里有大量重复的动作。这里写一次、编个号，旅程用编号引用，避免同一段判据在十三处各写一遍而彼此漂移。

**每条必须写明它是真实操作还是注入。** 这张表上一版没有这一列，后果是：旅程步骤写成「P4(某按钮)」，读起来像「点那个按钮」，而 P4 的定义里第一件事是发一条命令把控件唤出来。P4 被引用十二次，十二次都没人回头看定义。**这层编号本是为了减少重复，实际把注入藏了起来。**

### 驱动方式的规则

**默认是真实操作：合成触摸落在真实控件上，走完命中测试与手势识别，再由送达判定确认应用收到。每个操作前后各一张截图。**

**注入只在一种情况下允许**：Panorama 与 Docked 下 RealityKit 的碰撞体收不到合成手势，因而播放控件无法被唤出。此时允许注入**把控件显示出来**，然后**仍然要真实点击那个控件**。注入不得替代点击本身。

**每一处注入必须在表中标出三件事**：为什么非用不可、它跳过了哪一层、因此哪一类缺陷在这一步是看不见的。已知的教训是具体的——整窗第二块玻璃板挡掉所有非滚动控件输入的那个缺陷，症状像按钮坏了、实则在共同祖先，**恰好就位于注入跳过的那一层**。绕过命中测试的验证，在我们已经踩过坑的地方是盲的。

### 2026-08-20 真机实测：菜单宿主根本点不到

先决问题已在物理设备上跑出结论，比预期严重。

**做法**：切到设置页签 → 按 label 点「Default Scenic Environment」的取值按钮（SwiftUI Menu 的宿主）。

**结果**：`元素存在但当前不可命中`。重复两次，中间执行过 activate，均相同。该元素在层级中 `isEnabled=true`、`isHittable=false`。

**同屏阴阳对照**（这一步不可省，否则结论可能只是会话或窗口焦点问题）：
- 左侧栏 `Settings-category-storagePrivacy`、`Settings-category-about`：**点按成功**。
- About 面板的「View」按钮：**点按成功**。
- About 面板的「Copy」按钮：**不可命中**。

对照成立：同一屏内普通 Button 可点，**SwiftUI Menu 宿主不可点**。这不是通道故障，是产品侧的可命中性缺陷。

**因此 `selectMenuItem` 当初不是图省事，是当时唯一能走通的路——菜单宿主本身就点不开。** 但按应用内可达性承诺，结论不变且更明确：

1. **这是产品缺陷，开单修产品**（换控件形态，或补一个可命中的语义节点）。
2. 修好之前，涉及菜单的旅程步骤**一律显式标为注入**，并在报告中写明「本轮未验证菜单打开与命中测试」。
3. **可达性矩阵里那五条设置菜单的 reachable 判定必须撤销**——它们只证明了注入可达，而真实点按已实测不可达。

**第二处观察（仅一次，待复现后定性）**：点 `Settings-category-playback` 报告送达成功，但详情区仍停在 About 面板。「送达成功而界面不跟随」正是送达判定这一层存在的理由；需再跑一次确认是缺陷还是我的快照抢跑。

## 基元完整定义

### P0 起测试会话、验通道

执行：ensure-session 新起常驻 XCTest 会话（旅程之间不复用会话）；探针健康检查：写入随机内容、取回、SHA256 比对、清空。
成功：会话就绪且探针往返一致。失败：本旅程作废（通道故障，不计缺陷），进入恢复阶梯（会话重建→残留进程清理→设备重启一次；重启后以 devicectl 的 passcodeRequired 与 unlockedSinceBoot 字段判读状态，Xcode 错误字符串不构成终局证据，等待后重试）。

### P1 清库、重启、切页签

执行：通道动词 resetState(libraryFolder="Journey Fixture")——先删内存库中全部媒体引用（防止退出时回写持久化）、回到根后逆序删全部库文件夹、删全部 enchron.* 与 server-certificate-fingerprint.* 前缀 UserDefaults（后者是已记住的服务器证书，产品无忘记入口，不清则证书信任询问只能触发一次）、新建指定空文件夹；不触碰 TestMediaInbox（harness 暂存区）。然后 relaunch（terminate 加 launch）；tap 对应 Navigation-Ornament-tab-*，探针确认 delivered tab=目标。
成功：库为空且仅含指定文件夹；应用落在目标页签。失败：旅程作废。

### P2 把文件加进库

**当前是注入，必须改。** 现行做法是一条应用命令直接把暂存区的文件入库，网格上凭空出现卡片——**整个导入过程没有发生**：管理菜单没打开、系统选择器没出现、文件没被选中。而「导入」本身就是产品能力之一，被这条命令整个跳过了。
改后：主机侧 devicectl copy 把文件送进设备暂存区（这一步是布景，不是产品操作），随后**真实点击管理菜单里的导入入口**。系统文件选择器属系统域，人工层每场次走一遍；应用内那一段必须真点。
过渡期：改造完成前保留应用命令，但每次使用**在报告中显式列为一次注入**，并标明「本轮未验证导入界面」。
成功：库列表与网格均出现该媒体。失败：内容条件未满足，旅程作废（不计缺陷，报告列入附录 C 现场核对项）。

### P3 点卡片开播到稳态

执行：P10 包裹下 tap 网格卡片；轮询诊断串直至 lifecycle=Playing 且呈现字段等于预期；上限 40 秒。随后立即执行 P8（采帧判读）确认真实内容。
成功：稳态达成且 P8 判读通过。失败：本步失败（40 秒未稳态、或 P8 判黑屏/纯色/冻结）。

### P4 唤出控件并点击

分两种情形，**不再一律注入**：

- **窗口态与 Portal**：控件由点击视频表面唤出，这是真实用户路径，**必须真实点按**（J07 步骤 3 已在这么做）。此处使用注入等于跳过一条产品路径。
- **Panorama 与 Docked**：控件唤出依赖 RealityKit 碰撞体接收 tap 手势，而合成触摸落不到碰撞体上。**这是唯一允许注入的地方**：注入只负责让控件显现，**随后仍然真实点击目标控件**。本处注入跳过的是「唤出手势本身」这一层，因此该层的缺陷在本步看不见，报告中逐次标明。

两种情形之后都一样：单目标用 tap，连续多目标用 tapSequence（控件自动隐藏窗口撑不过多次通道往返）；每次点按经 P10 送达判定；**操作前后各一张截图**。
成功：目标送达。失败：目标不在层级或不可命中→记「够不着」签名（触发第 0 层定向重证），本步失败。

### P5 打开菜单并选中一项

**这是全表注入最深的一条，正在改。**

现行回退路径 `selectMenuItem` 的实现是：往通知中心发一条消息，视图订阅到之后直接调用该菜单项的动作。**菜单没有被打开、没有任何触摸、没有命中测试、没有手势识别。** 上一版把它描述为「进入与用户点击相同的产品处理器」——关于处理器这句是真的，但它被当成了「等价于用户操作」的理由，那是假的。它跳过的正是我们已经踩到过真实缺陷的那一层。

改后：P4 真实点按打开父菜单 → **子项按 identifier 或 label 真实点按** → P10 送达判定。
**先决问题（上机十分钟可定）**：SwiftUI 的 Menu 会剥离子项 identifier，但 label 是否仍可命中未验。证书信任的两个按钮无 identifier 而按 label 点到了，说明通路存在。
- 若菜单子项按 label 可命中：`selectMenuItem` 从全部旅程删除。
- 若确实不可命中：按应用内可达性承诺，**这是产品缺陷，开单改产品**（换控件形态或补可命中的语义节点），不是留着注入绕过。

成功：真实点按后产品选择处理器探针出现。失败：目标不可命中即本步失败并记「够不着」签名；**点击返回成功但探针未出现同样判失败——点击成功从不是送达证据**。

### P6 进入 Docked

前提：播放稳态且投影为 Flat。执行：P4 以 tapSequence 连点 TopAction-dock 与 DockMenu-指定环境；轮询 PlayerUI-spatial-state 直至九项空间事实全部成立（attached=docked、renderer 像素非零、surfaceSettled=true 等），上限 30 秒（presentationSettlementDeadline）。
成功：九项俱真。失败：本步失败并存快照。

### P7 经格式编辑器进入 Panorama

执行：P4 打开 videoFormat 编辑器（产品 open 探针确认，不以面板出现为准）；P5 语义选投影与立体（identifier 含度数符号原样拼接）；tap apply → 同时满足：presentation=portal、attached=portal、transition=none、pendingSpatialEffect=none、投影/立体/revision 已更新、Portal 请求 1280×720。再 P4 点 TopAction-resumePanorama → 沉浸探针 settle=true 且 RealityKit 采用所选投影。
成功：两段各自判据全部成立。失败：任一字段不满足即本步失败（禁止只看部分字段）。

### P8 采帧交 Agent 判读

执行：控制器截图 3 张，间隔至少 1 秒。机械预检：分辨率非 1×1、非纯色直方图（继承「工具报成功但输出垃圾」教训）。Agent 判读：内容真实、帧间连续、无整体色偏、符合场景预期（如 HDR 无灰雾）。判读结论与帧一并归档。
成功：机械预检过且判读通过。失败：判读不通过为本步失败；预检不过为证据无效（重采一次，再不过旅程作废）。

### P9 麦克风采音判读

执行：麦克风采集不少于 5 秒 → 音频分析工具输出结构化结果 → 与预期特征比对（预期频率主导、非静音、或指定切换后频率变化）。
成功：特征匹配。失败：静音或特征不符为本步失败。

### P10 送达判定

执行：动作前记录探针偏移 → 执行动作 → 取探针增量查找预期送达标记 → 三级记录：存在层级、可命中、应用已送达。三者俱全才记通过。
纪律：驱动而未评估送达 = 未评估，永不记缺陷；本判定是唯一写入点，任何步骤不得旁路。

### P11 终态核对

执行：回到预期界面；诊断串无 userVisibleIssue；旅程涉及的持久化状态逐项复核（listLibrary、设置值、进度）；本旅程证据段末批量取回归档。
成功：清单全部成立。

### P12 音轨字幕各切三次

共享段落，四条来源旅程逐字复用同一序列，只有片源来自哪个来源不同。这是「同一片源经不同来源进来，交互机器表现一致」的证明装置；判据在各来源间必须完全一致，任何来源上的差异即该来源的缺陷。

前提：汇总片源 sdr-bframe-aggregate-30s.mkv 已在稳态播放（P3 通过）。

执行：
1. 音轨连续切换三次：P5(more 菜单, audio 家族) 依次选 FLAC 660Hz → AC-3 440Hz → E-AC-3 550Hz，跨越解码与透传两条管线。每次切换双重验证——机械层：重新 listMenuItems 断言目标轨 isSelected=true，lifecycle 保持 Playing，position 持续推进；判断层：P9 主导频率翻转到目标轨频率。

3. 远程来源附加断言：切换期间不重开会话（renderer 与 session 身份不变），字节流未中断。

成功：六次切换全部双重验证通过。失败：任一次不通过即本段失败——连续切换可行性是本段的证明目标，不允许「三次里过一次」。
内容条件：外挂边车须与视频同目录同基名。远程来源上若边车缺失，字幕第三次切换记为内容条件缺口而非缺陷。

### P13 切换过程取证

用于 J06 与 J07 的连续切换段。**采集能力的边界是实测的，不是假设的**：

- 系统级屏幕捕获在本 visionOS 构建上返回 1×1 图像，控制器因此退回抓应用元素截图（`InteractiveDeviceUITests.swift:330-338` 的注释即为此）。
- 屏幕录像只有 VisionProCoreRegression 计划请求（`preferredScreenCaptureFormat: screenRecording`），而历史 result bundle 中**从未产出任何视频负载**（抽查四个 bundle，视频文件数皆为 0，体积仅 28K）。**录屏当前不可用，不得写入执行计划。**
- 控制器截图往返中位数 2.71 秒（`controller_timings.json`，20 次样本）。呈现切换远快于此，**连续截图在原理上无法采到切换中间态**。

因此本基元按能拿到的证据分三层：

1. **前后帧（可执行）**：切换前一帧、切换后稳态一帧，经 P8 判读。回答「切换后画面是否正确」，不回答「切换过程中发生了什么」。
2. **结构计数（可执行，主判据）**：每次切换读取诊断串与字节流统计——会话身份、渲染器身份、streamEpoch、flushCount、已接受连接数。这一层才是抓复用路径回退的东西，且不受采样率限制。
3. **应用内探针时序（可执行，用于时间对照）**：探针日志每行带 ISO8601 时间戳，且已记录 `presentation X -> Y` 与 pendingEffect。切换耗时取自**应用内两条探针的时间差**，绝不取控制器往返耗时——后者 2.7 至 4 秒，比被测对象大一个数量级，用它测切换等于只测了往返本身。

4. **状态环（已实现并经单元层锁定，附录 D9）**：切换过程的第四层证据。应用按渲染器节奏把 `graphRevision`、`acceptedInputCount`、`displayedFrameObservationCount`、`actualTimebaseRate`、`streamEpoch`、`flushCount` 连同单调时间戳写入有界环，切换结束后整批取回。它使下列四个量可被**机械推导**，不再依赖判读：
   - 切换耗时＝从呈现态改变到新渲染器图上首个显示进度前进
   - 切换期间显示进度停滞的最长连续时长（黑帧与旧帧残留的可测代理）
   - 时基速率是否跌零及持续多久（停顿）
   - 图版本变化次数与字节流连接数增量（复用路径回退）

   **保守性**：显示缓冲的 IOSurface 身份可能在内容更新时保持不变，故显示进度只能作保守信号——它前进即证明有新内容，它不前进不等于画面静止。判据据此写成单侧断言。

   **截断标注**：每次切换另带左截断与右截断两个标志。证据窗口开头已被环覆盖，或采集在切换完成前就结束时，该次切换被标为截断而非给出一个偏小的数。截断的切换不参与判据，只作为「本次未取到证据」记录。

   **记录器的开启与关闭**：环只在测量期间接收记录，其余时间采样点提前返回。开启由取证方在切换前显式发起，关闭在整批取回后发生。

   **采样密度是这件工具的存亡属性**：环的算术正确而采样过稀时，停滞与跌零两个量测的是记录间隔而非真实停滞，且整套单元测试照样全绿——喂进合成样本只能验算术，验不了覆盖。因此采样密度由一条专门的断言锁定：记录器开启时每接受一个视频样本产生一条记录，关闭时一条不产生。这条断言不验算术，它只防采样点退化。

   **开销**：关闭时成本仅为一次锁获取。开启时每样本多做一次显示缓冲观测，而该观测本就已在每样本的诊断路径上发生，故额外开销是同一次观测的翻倍，且限于调试构建。首次真机整跑时对照一次开启与关闭状态下的切换耗时，确认工具未扰动被测对象。

   **过程证据的边界**：切换过程中产品会主动暂停送帧，此时按样本采样自然停止，过程分辨率退回到每秒十次的周期采样；周期采样由时基推进驱动，时基停住时它也停。三者同时静默的那段间隔被完整归给最后观测到的状态，因此停滞时长仍被正确计入，但**过程中间态的逐点状态不可得**。**不要用前后帧冒充过程证据。**

## 结构检查

1. **偏好项独立性**：每个播放偏好项只允许一处生产读取点。多出一处即报错并要求显式说明耦合理由。这条守住的是 J10 C 段「逐项验证即完备」的前提——前提一旦失效，逐项测试仍会全绿，设备回归发现不了。
2. **孤儿类别**：十五个类别当前均有产生者。若将来某个类别失去全部产生者，它就变成不可能出现的死表达，而设备回归永远发现不了这件事——没有产生者就没有触发，没有触发就没有失败。这属于结构检查，写进闸门。

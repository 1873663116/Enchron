## KI-007：首播黑屏仍在 5 秒量级，且切换视频时旧画面 / 旧控件会残留到新视频首帧出现前

### 现象

- 2026-03-10 最新用户实测：首次打开视频时，黑屏加载仍然大约需要 5 秒。
- 切换到另一个视频时，旧视频的画面和控件会继续停留在窗口里，直到新视频真正加载完成后才被替换。
- 用户预期是：关闭旧视频的一刻，就应立即把旧画面和旧控件从前台卸载；进度保存和其它持久化应在后台完成，而不是等到打开下一个视频时再感知到。

### 当前最高概率解释

这不只是“首播慢”，而是**播放启动、播放关闭、媒体信息刷新和 UI 呈现仍然耦在一起**。

1. `MainView` 现在采用常驻挂载的 `WindowVideoView`，这是为了提前 attach layer 和 warmup，但也意味着如果不主动清空显示态，旧帧会自然残留在 surface 上。
2. `PlaybackLaunchCoordinator.beginPlayback(for:)` 会先把 `appModel` 切到正在播放，再等待新链路真正开始；如果新媒体的首帧和媒体 profile 都还没到，用户看到的就仍是上一段视觉状态。
3. `WindowVideoViewModel.currentMediaProfile` 与控制栏二级信息 UI 依赖 `onMediaProfileDetected` 回调，而这个回调发生在播放器已经开始 probe 之后，不是用户点击文件的瞬间。
4. 关闭路径和持久化路径还没有形成“前台立即卸载、后台异步保存”的明确分层，因此“旧内容滞留到下一次打开”仍然是可感知问题。

### 修复方向

1. 把“视觉卸载”和“后台持久化”彻底拆开：用户关闭视频时，前台应立即清空旧 frame / 旧 profile / 旧控件态。
2. 在新视频首帧出现前，不继续复用上一条媒体的 profile 驱动控件文案。
3. 新视频在 profile 尚未识别完成前，可以选择不加载播放控件，避免先显示错误控件、再替换成正确控件。
4. 为切换播放单独补阶段日志，至少拆出：旧会话 teardown 开始、surface 清空、persist queued、新请求开始、profile ready、首帧可见。
5. 若常驻 surface 继续保留，则必须补一层“空白占位态”，不能让旧 drawable 继续充当前台内容。

### 调查状态

- 状态：开放中
- 结论类型：用户 2026-03-10 实测 + 当前代码路径一致的高概率解释

## KI-008：播放控件视觉仍未达标，`±10s` 依旧不够显式，tracks / playlist 二级菜单也没有对齐系统容器逻辑

### 现象

- 用户明确反馈：当前新控件普遍叠加了明显的黑色底板，视觉质量退化，和 visionOS 原生感不一致。
- 左右 `快退 10s / 快进 10s` 按钮仍然不显示。
- 音轨 / 字幕面板与选集面板，当前仍未对齐倍速菜单所使用的系统菜单容器和动画逻辑。
- 现阶段只有倍速菜单更接近“系统原生方案”，其余二级菜单仍然显得像另一套 UI 体系。

### 当前最高概率解释

上一轮修正过度把问题理解成“控件需要稳定底板”，结果走到了**对比度修复了，但美术方向偏了**。

1. 共享按钮样式统一后，使当前底板过重，破坏了质感。
2. `±10s` 作为主动作两侧按钮，当前视觉权重仍不足，图标与底板关系没有拉开层级。
3. `tracks` / `playlist` 仍走自定义 floating panel，而不是优先使用系统原生的菜单 / 容器语义，所以动画和质感与倍速菜单不一致。

### 修复方向

1. 回到“系统原生优先”的路线：简单二级菜单优先用系统 `Menu` / 系统容器，不再继续堆自定义 panel。
2. 重新定义主控件的层级：播放、`±10s`、时间轴入口是一级视觉；tracks / playlist / 倍速是次一级。
3. 去掉所有控件“黑色底版”。
4. 在 visionOS Simulator 和真机上分别复测主控件可见性、命中确认感和层级关系。

### 调查状态

- 状态：开放中
- 结论类型：用户 2026-03-10 实测

## KI-009：二级时间轴的边界、默认缩放和拖动映射仍不正确

### 现象

- 2026-03-10 用户继续实测确认：当视频到最后一帧时，二级时间轴本体没有被完全拉到最左边；回到第一帧时，也没有被完全拉到最右边。
- 用户预期的默认态是：时间轴初始显示应处于最小宽度，也就是只占最大极限宽度的一半；随后随着缩放往右拉，时间轴本体再逐渐变长。
- 当前实现虽然已经接近“本体伸缩 + 视口裁切”，但首尾帧映射与默认态仍然没有完全对齐用户预期。

### 当前最高概率解释

问题已经不再是“圆角矩形里塞刻度”这种老实现，而是**几何模型和用户感知预期之间还差最后一层对齐**。

1. 现有 `DetailedTimelineGeometry` 已经具备 `timelineWidth`、`contentOffset`、`secondsPerPoint` 这些核心量，但首帧 / 尾帧的视觉边界和默认缩放态仍未完全匹配用户预期。
2. 时间轴默认缩放虽已收敛到最小宽度因子 `0.5`，但默认展示状态、首尾 frame 的视觉落点、以及用户“最左 / 最右”的直觉仍有偏差。
3. 对用户而言，判断标准不是内部公式，而是“第一帧时本体最靠右、最后一帧时本体最靠左”，这一点当前仍未过关。

### 修复方向

1. 以用户可见几何为准重新校准首尾帧边界，而不是只以内部 offset 数值自洽为准。
2. 把默认进入二级时间轴时的缩放态、首帧位置和当前播放时间的初始对齐一并复测。
3. 补一轮以“首帧 / 中间 / 末帧”为中心的 geometry regression test，并在 simulator 上做肉眼 smoke。
4. 本问题在体感上属于产品核心交互资产退化，不应继续以“逻辑大体正确”作为收口标准。

### 调查状态

- 状态：开放中
- 结论类型：用户 2026-03-10 实测

## KI-010：HDR 内容识别已经更准确，但 HDR 入口、切换能力和真实输出都还没有形成最终产品方案

### 现象

- 用户 2026-03-10 明确确认：HDR 内容类型本身现在识别更准了。
- 但当前一级播放控件不适合作为 HDR 标签和 HDR / SDR 切换的稳定宿主，因为首次打开时相关信息仍可能晚到。
- 用户已明确给出新的产品方向：HDR 标识、HDR / SDR 切换、分辨率、帧率、文件大小等信息，都应放进一个新的 `i` 二级信息面板中。
- 即使改到二级信息面板，用户仍然要求在打开一级控件后立刻进入该面板，因此 HDR 信息识别依然要尽可能前置，尤其是远程源。
- 与此同时，当前真实输出仍然只是 `SDR Preview`，而且正式的 HDR / SDR 切换能力也还没有真正开放成可用功能。

### 当前最高概率解释

这说明当前问题已经分成两层：

1. **信息呈现层**：HDR 信息应该迁移到新的 `i` 二级信息面板，而不是继续在一级播放控件上争抢位置。
2. **识别 / 输出层**：即使入口迁移了，HDR 信息仍然不能太晚到；同时真实 HDR 输出和 HDR / SDR 切换功能本身也还没完成。

更具体地说：

1. 现有 `currentMediaProfile` 由播放器在打开媒体后回调，不是文件浏览阶段已有信息。
2. 因此不管 HDR UI 放在一级控件还是新的 `i` 面板，只要 profile 仍然晚到，就会遇到“先打开的是空 / 旧状态，稍后才刷新”的问题。
3. 对远程源尤其明显，因为 metadata 获取和首帧准备本身就更慢。
4. 另一方面，当前 `hdrOutputMode` 虽然已经说真话了，但产品目标并不是长期停留在 `SDR Preview`，而是要真正完成 HDR 显示链路并开放切换能力。

### 当前产品决策

- HDR 标识和 HDR / SDR 切换，不再要求挤在一级播放控件里。
- 新增一个 `i` 信息按钮，进入二级信息面板。
- 该面板至少承载：HDR 类型、HDR / SDR 切换、分辨率、帧率、文件大小。
- 这不意味着可以接受“晚识别”；用户打开一级控件后应能立刻进入该面板并看到可靠信息。

### 是否可以做到“点开时就准备好”

可以，但**前提不是继续等当前播放链路自己告诉 UI**，而是新增一条**播放前 metadata probe / cache 链路**。

更具体地说：

1. 如果要做到用户刚点开视频，一级控件打开后立刻进入 `i` 面板就能看到正确 HDR 信息，那么浏览层必须在播放前或播放启动极早阶段就已经拿到 `MediaProfile`。
2. 对本地文件，这通常可通过轻量 probe 提前读取容器 / 码流 metadata。
3. 对远程源，也不是不可能，但必须明确设计“浏览时预探测”或“点击后先 probe 再建播放会话”的链路，而不能继续完全依赖 mpv 播放时的首轮 probe。
4. 用户当前判断是：只要 `KI-007` 的切换 / 首播链路彻底理顺，这里的“信息晚到”问题大概率会自然缓解；因此这两条问题应联动解决，而不是拆成互不相干的两个局部补丁。

### 修复方向

1. 新增 `i` 信息按钮和二级信息面板，承载 HDR 类型、HDR / SDR 切换、分辨率、帧率、文件大小等信息。
2. 让 `KI-007` 的切换链路先收口：旧媒体关闭即卸载，新媒体未识别完成前不加载错误控件。
3. 新增“播放前 `MediaProfileProbe`”能力，把 HDR 类型、分辨率、帧率等信息从播放链路中前置出来。
4. 浏览层缓存 probe 结果，点击播放时直接把 profile 带入新的播放会话，特别是远程源也要有可落地方案。
5. 正式完成 HDR 显示链路，不再长期停留在 `SDR Preview`。
6. 正式开放可验证的 HDR / SDR 切换能力，而不是只在文案层保留状态名。

### 调查状态

- 状态：开放中
- 结论类型：用户 2026-03-10 产品决策 + 当前架构推断

## KI-011：SMB 现在是 IP-only 输入，但应用侧仍未真正接入 AMSMB2，因此连接直接在库缺失处失败

### 现象

- 用户 2026-03-10 实测：SMB 输入框现在确实只允许输入 IP 地址。
- 但连接时仍然失败，错误信息明确提示需要 `AMSMB2` / “SMB2 什么的”。

### 当前最高概率解释

这不是新的地址解析 bug，而是**应用工程当前根本没有把 AMSMB2 真正接进来**。

1. `SMBDataSourceAdapter.swift` 使用 `#if canImport(AMSMB2)` 分支。
2. 如果工程没有实际集成该库，就会落入 stub 实现并直接抛出 `SMBError.libraryNotAvailable`。
3. 当前仓库检索没有发现 `AMSMB2` 被加进主工程依赖，因此用户现在碰到的是“库未接线”，不是“协议流程又错了”。

### 修复方向

1. 先把 `AMSMB2` 正式接入 Xcode 主工程，而不是只在文档里写“依赖它”。
2. 真机上重新验证：仅输入 IP、用户名、密码后，应先登录服务器，再拉取 share 列表。
3. 在库未接入的阶段，错误提示应更明确地区分“功能未打包”与“服务器连接失败”。

### 调查状态

- 状态：开放中
- 结论类型：代码静态证据 + 用户 2026-03-10 实测

## KI-012：持久化最小实现已不再崩溃，但“关闭即卸载、后台保存”和“通过 Persistence adapter 统一落盘”仍未真正收口

### 现象

- `UserDefaultsStore` / `SwiftDataStore` 已不再是 `fatalError("TODO: implement")`。
- 但用户当前最在意的关闭体验还没有解决：关闭视频时没有做到前台立即卸载、后台异步保存。
- 已保存数据源仍然由 `FileBrowsingViewModel` 直接写 `UserDefaults.standard`，没有走 Persistence 抽象。

### 当前最高概率解释

本问题已经从“缺实现”变成了**实现存在，但还没真正接到产品主链路上**。

1. 最小 adapter 已可读写偏好、进度和屏幕位置。
2. 但文件浏览的已保存数据源仍然旁路落盘，Persistence 边界并未真正统一。
3. 这也解释了为什么“关闭即卸载、后台保存”目前还只是预期，不是现成能力。

### 修复方向

1. 把关闭视频时的 progress 保存明确串到后台任务，而不是等下一次播放时感知。
2. 让已保存数据源也通过 Persistence adapter 落盘，不继续直写 `UserDefaults.standard`。
3. 对“关闭视频”与“切换视频”分别定义持久化时机，避免用户在前台看到保存动作。

### 调查状态

- 状态：开放中
- 结论类型：代码静态证据 + 用户 2026-03-10 体验诉求
